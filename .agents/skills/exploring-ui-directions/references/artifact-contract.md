# Comparison Lab Artifact Contract

## File boundary

Create exactly one disposable HTML file. Inline all HTML, CSS, JavaScript, icons, and synthetic data. The artifact must work without a build step, package install, application server, or network dependency.

Do not add a production route, import application modules, mutate product data, or create companion files. The artifact may visually reproduce the relevant app shell from inspected project evidence.

## Shared comparison frame

Define one realistic core task before drawing directions. Build one synthetic dataset that supports that task and reuse the same records, labels, states, and constraints in every direction.

Place an explicit notice near the top:

- Every person, organization, record, and metric is fake.
- No real user or customer data is loaded.
- No product code or route was changed.

Distinguish existing capabilities from future concepts. Never make an unbuilt action look operational without labeling it.

## Attention order

Order sections by decision value, not by the chronology of the design process:

1. Purpose, fake-data boundary, and the core decision.
2. Two to four project findings that materially constrain the concepts.
3. Direction selector, one-line philosophy, full interactive frame, and critique.
4. Product boundaries or sequencing only when they determine the structure.
5. At most five build-changing open questions with concrete trade-offs.
6. Notes and the copyable reply assembler.
7. Technical wiring note.

Keep repository research concise. The interactive comparison deserves most of the visual weight.

## Direction anatomy

Default to four directions. Each direction must include:

1. **Name:** short, memorable, and specific to its structural bet.
2. **One-line philosophy:** one sentence that states what the direction optimizes and what belief it makes.
3. **Full frame:** show the surface inside the current product shell or a credible adjacent context, not as an isolated card.
4. **Behavior:** make the primary task usable and include the interactions needed to feel the model, such as switching scope, navigating hierarchy, filtering, searching, opening details, or changing placement.
5. **Steal chips:** provide 2 to 3 concrete, transferable details. Good: "persistent workspace tree with item counts." Bad: "clean and modern."
6. **Skip chip:** state at least one honest failure mode, cost, or context where the direction is wrong.
7. **Winner control:** let the user choose this direction directly.

Keep winner and steal selections when the user switches directions.

Before implementation, compare candidate directions across these axes:

- Information architecture and hierarchy
- Density and scanning model
- Metaphor or mental model
- Navigation and placement
- Scope and ownership
- Primary interaction

Every direction must make a meaningfully different structural bet across at least two axes. If two concepts differ mostly in styling, replace one.

## Product questions and variants

When global-versus-profile scope, navigation placement, or another structural dimension is unresolved, add a useful toggle that changes the frame so the user can experience the difference.

Ask only questions whose answers change routes, ownership, permissions, data modeling, or component architecture. Limit the artifact to five questions. For each:

- Offer concrete options.
- Explain the consequence or trade-off in plain language.
- Preselect a recommendation only when evidence supports one.

Do not use rating scales, weighted scoring, or a complex hybrid builder. Direct choices reveal enough.

## Feedback and reply assembly

Include:

- One winning-direction choice
- Selectable steal chips from any direction
- Selected answers to build-changing questions
- One freeform notes area
- One live-updating, read-only reply
- One copy button with a clipboard fallback

Assemble plain text in this shape:

```text
UI direction feedback

Winning direction: [name]
Details to steal: [selected details or none]

- [Build-changing question]: [answer]

Notes: [freeform notes, omitted when empty]
```

Do not force every field before copying. Preserve the user's exact notes.

## Visual and content integrity

- Derive colors, typography, spacing, radii, icon style, component language, and copy voice from the actual project's design system.
- Reuse recognizable shell and navigation patterns without importing production code.
- Respect local accessibility, brand, privacy, and copy rules.
- Avoid generic AI styling such as default purple gradients, excessive glass effects, decorative glow, interchangeable dashboard cards, or unexplained pill controls.
- Use semantic controls, visible focus, clear selected states, reduced-motion support, and responsive layouts.
- Keep decorative detail subordinate to comparison and task behavior.

## Wiring note

End with a compact note that:

- States that no real application code was touched.
- Names actual likely project paths for the future route or screen, navigation entry, reusable components, data access, and design tokens.
- Calls out any required schema, permission, privacy, or migration decision.
- Separates reuse from new work.

Use only paths verified in the repository. If a likely path is unknown, say so rather than inventing one.
