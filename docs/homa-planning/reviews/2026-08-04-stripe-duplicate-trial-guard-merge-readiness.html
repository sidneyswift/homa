Stripe duplicate-trial guard

Branch: codex/stripe-duplicate-trial-guard
Scope: 14 implementation, migration, test, and evidence files before this review artifact.
Release shape: application deploy first, then additive migration verification. No destructive schema change.

Mental model

Before

Stripe Checkout completion or its webhook stamped trial_started_at. A new email and device could create a second subscription with the same card. Homa had no provider-level equality signal.

After

Verified Stripe subscription → retrieve its card payment method → atomically claim its provider fingerprint → either stamp the trial or cancel the later subscription → show a private account-recovery path. The webhook runs the same guard for closed-tab checkouts.

Non-obvious behaviors

Exact card signal, not identity matching

What: only Stripe card fingerprints can block a trial. Name, email, child data, IP address, and device identity play no part.

Why: a false positive would expose or conflate unrelated families. Missing and non-card signals safely proceed.

Where: apps/web/lib/billing/duplicate-trial.ts:47-58,117-134.

Race-safe ownership

What: one database primary key serializes concurrent claims. The same family can retry; another family can claim only after the prior owner is explicitly lapsed.

Why: a read-then-write check would let two concurrent checkouts both pass.

Where: apps/web/lib/billing/duplicate-trial.ts:60-100, supabase/migrations/20260805200000_reconcile_trial_claim_migration.sql.

No new entitlement for the later checkout

What: the duplicate branch cancels the Stripe subscription and exits before startFamilyTrial or subscription mirroring.

Why: cancellation alone is insufficient if the product already unlocked the second family.

Where: apps/web/app/api/billing/confirm/route.ts:106-117, apps/web/app/api/billing/webhook/route.ts:104-128.

Privacy-preserving recovery

What: the later family sees a reassurance and a sign-in link, not any account, family, or card details. Analytics carry only the local family ID.

Why: a card match must never disclose that another family exists.

Where: apps/web/components/billing/trial-gate.tsx:129-141, packages/core/src/events.ts:1479-1485.

Existing behavior this relies on

Stripe must provide a card payment method and a stable fingerprint. Wallet-token and non-card checkouts intentionally remain outside this exact guard. Stripe’s cancellation API must remain idempotent for an already-canceled subscription.

The production database must receive migration 20260805200000_reconcile_trial_claim_migration.sql. Issue #873 supersedes the original filename after a duplicate version prevented the table from reaching production. The isolation check is already armed to prove the final RLS posture.
