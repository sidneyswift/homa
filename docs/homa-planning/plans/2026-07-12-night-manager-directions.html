Where should the night manager live?

An agent that reads customer usage and chats every night, then proactively identifies and fixes bugs, improvements, and features. This lab lays out ten codebase-grounded ways to get there, cheapest to most ambitious. Tap what resonates; the bottom of the page writes your reply for you.

Disposable artifact · every claim below cites a real file or a doc checked 2026-07-12 · nothing here touches the app
The one structural finding: this is two jobs, not one. The analyst (read usage and chats) needs production data credentials and must respect MJ-13 and tenant isolation. The builder (fix and ship) needs repo, CI, and PR credentials. Your own codebase already keeps these apart: the product agent's shell is disabled by founder ruling (agent/tools/bash.ts) and its sandbox egress is deny-all (agent/sandbox.ts). The strongest designs below keep that split on purpose.

Turn on the founder digest that is already built

S · tonightwiring

Not an agent, but the first rung of "something watches the fleet every night and tells me". One env var lights it up.

Found in codelib/admin/digest.ts is complete: signups, failed and uncertain sends, rejected emails, task-run trouble, quiet-family count. ImpactEvery later option reuses this delivery rail and this reading habit. Zero code, zero risk, and you start learning what a useful night report contains.

Turn on the reactive reviewers: Vercel Agent and Bugbot

S · this weekvendor config

Before an autonomous agent opens PRs at 3am, give the repo independent reviewers that never sleep. This is the safety net that makes every builder option below cheap to trust.

Found in code / verifiedThe repo deploys on Vercel (apps/web/vercel.json, deploy laws in AGENTS.md). Vercel Agent (code review with sandbox-validated patches, production investigations, approved actions) went public beta 2026-06-30 for Pro and Enterprise teams; review pricing is $0.30 plus tokens. Bugbot and security-review subagents are already installed in your Cursor toolkit.
ImpactNight-manager PRs get an independent review before you wake up. Investigations also cover the "why did errors spike" half of night management reactively.

3

The analyst: a nightly night-report schedule inside the product

M · a day or twoin-product code

A third eve schedule, cloned from the fleet-research pattern: the handler queries the fleet ledgers deterministically, the model turns them into findings (bugs suspected, friction seen in chats, feature demand, spend anomalies), and the result lands as an email plus a saved report.

Found in codeagent/schedules/fleet-research.ts already proves the whole shape: nightly cron, env-flag kill switch, own channel (agent/channels/research.ts) with its own instruction mode, run rows in homa_task_runs. The dispatch schedule proves the "handler builds context, model composes" pattern via loadBriefContext.
Tenant isolation keptThe model never gets a database tool. The handler (deterministic TypeScript) runs the adminDb() aggregates and hands pre-redacted context in the prompt, the same way the morning brief does. Chats stay inside the product trust boundary where they already live.
ImpactThis is the half of your ask that reads usage and chats. It cannot fix anything, and that is a feature: it has no repo credentials to leak family data into.

4

The builder: nightly GitHub Actions job running the Cursor CLI

M · a daydev platform

A cron workflow next to your CI: check out the repo, run agent -p headless with a night-manager skill, let it triage findings, update the backlog by PR, and open small fix PRs. Everything the builder is and does lives as versioned files in the monorepo.

Found in code / verifiedCI already lives at .github/workflows/ci.yml, so secrets and Actions habits exist. Cursor's docs (cursor.com/docs/cli/github-actions) show exactly this: install CLI, CURSOR_API_KEY secret, agent -p with a scoped prompt, deterministic git/PR steps around it.
Monorepo containmentBest of any option: the trigger (workflow YAML), the brain (a skill at .agents/skills/night-manager/SKILL.md, same convention as your existing skills), and the guardrails are all repo files reviewed like code.
ImpactMorning becomes a review queue: a handful of small PRs, each already gated by CI and option 2's reviewers. No new vendor, billing on the Cursor key you already have.
new: .github/workflows/night-manager.yml · new: .agents/skills/night-manager/SKILL.md · secret: CURSOR_API_KEY
5

The builder, alternate runner: a scheduled Cursor Automation

M · an afternoondev platform

Same brain, different trigger: a Cursor cloud agent on a cron schedule, scoped to the homa repo, opening PRs from an isolated VM. Configured in the Cursor dashboard rather than a workflow file.

VerifiedCursor Automations (cursor.com/docs/cloud-agent/automations) support cron triggers, single-repo scope, PR creation, and encrypted secrets via the Secrets tab. Runs appear in the Agents window; Slack and webhook triggers exist too, so you could also poke it by message.
Trade-off vs option 4Zero YAML and better observability inside the tool you already live in, but the schedule and secrets are dashboard state, not repo files. The skill file stays in-repo either way, so switching between 4 and 5 later is cheap.
reuses: .agents/skills/night-manager/SKILL.md · trigger + secrets: Cursor dashboard
6

Anthropic Managed Agents: a scheduled deployment

L · a few daysnew platform

Anthropic's hosted harness: define an agent (model, prompt, tools, skills), an environment (managed cloud sandbox or self-hosted), a vault, and a cron deployment. Each night a session wakes, works, and ends.

VerifiedScheduled deployments are live in beta (header managed-agents-2026-04-01): 5-field cron plus IANA timezone, pause/resume, manual test runs, run history. Vaults hold env vars and attach real keys only at the network boundary, only for allowlisted domains, so the sandbox never sees the secret. GitHub, memory stores, and files are supported.
Where it shines / where it rubsBest managed-sandbox credential story of any option (a Supabase key scoped to allowed domains via HTTPS). But it is a second vendor in beta, PR ergonomics are thinner than Cursor's, and deployment state lives on Anthropic; you would keep it honest with a config-as-code upsert script in scripts/.
platform.claude.com/docs/en/managed-agents · optional new: scripts/night-manager-deploy.mjs
7

The two-stage pipeline: analyst inside, builder outside

L · about a weekRecommended

Compose 3 and 4 (or 5) with one new seam: the in-product analyst writes a redacted findings report (aggregates plus exemplar quotes stripped of names and identifiers, per MJ-13) to a table, served at a founder-gated endpoint. The builder fetches that report, never the database, and works the repo: triage, backlog PRs, small fix PRs, a morning summary.

Why this is the structural winPrivacy stops being a blocker to autonomy. Raw chats never leave the product trust boundary; GitHub and the dev platform only ever see redacted findings. Each half is small, testable, and replaceable: swap the builder runner (4, 5, 6, or 8) without touching the analyst.
Found in codeEvery rail exists: nightly schedule pattern (fleet-research.ts), fleet queries (lib/admin/*), report delivery (digest.ts email plus an admin page), founder gating (lib/admin/gate.ts and requireFounder()), CI gates, and your review subagents. The new pieces are one schedule, one channel, one table, one endpoint, one workflow.
The morning loopYou wake to: one analyst email (what the fleet did, what hurt, what families asked for), a backlog PR (proposed tickets with evidence), and 0 to 3 small fix PRs each already reviewed by CI and option 2. You merge or close over coffee; founder rulings stay yours.
option 3 pieces · new: /api/admin/night-report (bearer-gated) · option 4 or 5 as the consumer

The Mac mini night shift

M build · high opsinfra you run

A launchd cron on the mini runs the Cursor CLI (or Claude Code) against a local checkout each night, with local env files for data access. It could also serve as a self-hosted sandbox for option 6.

Found in codeAGENTS.md's boundary list proves the machine exists and already holds live secrets and family data (homa-macmini/ is a hard do-not-touch in this workspace).
Honest trade-offsCheapest way to give one agent both database and repo credentials with no new cloud surface, and no per-run compute bill. But you become the SRE (sleep, updates, uptime), and it concentrates an autonomous dev agent on the same box as live family data, which weakens exactly the boundary the two-stage pipeline exists to protect.
launchd plist on the mini · same repo skill as options 4 and 5
9

A second eve agent in the monorepo (apps/manager)

L to XLre-scored 2026-07-12 evening

Originally marked "not recommended" on serverless-runtime grounds. Two June 2026 Vercel releases weaken that objection, so this card is re-scored: viable now, still the DIY path. A thin eve app, deployed as its own Vercel project, whose nightly schedule spawns a Vercel Sandbox that clones the repo, works, and opens a PR.

What changed (verified)Vercel Sandbox runs up to 24 hours on Pro (changelog 2026-06-16, up from 5), supports source: git clones of private repos, persistent snapshots across runs, per-sandbox egress policy, and 8 vCPUs on Pro. Separately, Dockerfile deploys landed 2026-06-30, but those are HTTP servers on Fluid compute (must listen on $PORT, scale to zero after 5 idle minutes), so they are a trigger surface, not the night worker.
How it would runThe schedule handler (not the model) creates the sandbox with a scoped GitHub token, allowlisted egress (github.com, npm, the model API), runs install plus the guard suite, and ships a branch via gh pr create. eve already ships the vercel() sandbox backend this repo uses in prod (agent/sandbox.ts), and its runs land in the same homa_task_runs ledger the founder console reads. Never run the work inside the function itself: function duration caps are minutes, the sandbox is the compute.
What it still costsYou hand-roll what Cursor and Anthropic sell: git credential custody, PR conventions, retries, a review surface, budget caps, and most of all the coding-harness quality gap. eve gives bash and file tools; Cursor's agent is a tuned coding harness. The pragmatic hybrid: the sandbox installs and runs the Cursor CLI headless (agent -p), so Vercel hosts the night shift while Cursor supplies the coder. Isolation law: separate Vercel project, separate env, no product service-role keys anywhere near it.
new: apps/manager (eve app, own Vercel project) · reuses: eve vercel() sandbox backend, homa_task_runs · vercel.com/changelog/vercel-sandbox-can-now-run-for-up-to-24-hours
