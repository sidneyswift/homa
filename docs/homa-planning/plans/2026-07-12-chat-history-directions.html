Comparison lab · first round

How should past conversation work?

Two things in one lab. First, a clickable map of how messages, sessions, episodes, and memories actually fit together in Homa today, and why two devices can show different chats right now. Then four genuinely different product shapes for finding and continuing past conversation, all on the same fake family, so you can judge the structure instead of the paint.

Every person, message, and record here is fake. No real family data is loaded. No product code or route was changed.

The core decision: when a parent wants yesterday's conversation (which may have happened on another device, over text, or in email), what does she navigate: one synced thread with search, a list of chats in the sidebar, a separate readable journal, or just Homa herself?
Core task held constant in every direction: it is Sunday on the laptop. Find Thursday night's plan for Maya (made on the phone) and Friday's text about scissors, then pick that plan back up.
Standing rulingFounder direction 2026-07-10: one family chat, not a ChatGPT-style thread list; day separators plus a fresh model session each morning. This lab exists because that ruling is being re-examined; a winner that contradicts it must update the ruling register.
The record already existsEvery message on every channel (web, text, email, Homa-initiated) is written server-side to conversation_messages the moment it happens. The devices-disagree pain is a render-source gap (each browser draws from its own cache until M1-02), not missing data.
Sessions are not chatsA session is the model's working memory: per device and channel, rotated after 4am. Episodes are the server's conversation grouping (messages that belong together, across channels). Any UI that lists raw sessions will show meaningless splits.
Memory lives outside threadsThe family context block, saved memories, and the recall search are rebuilt into every fresh session. Continuing a conversation never technically requires reopening it; the question is what the parent needs to SEE.

Wiring note (for the build after you choose)

    
No real application code was touched by this lab. Likely integration paths, verified in the repository:

    
    
      
  • Chat surface: apps/web/app/app/page.tsx + chat-client.tsx; render cache and 4am rotation in apps/web/app/app/chat-storage.ts; day separators in transcript-days.ts. Mobile twins: apps/mobile/src/features/chat/chat-session.tsx, apps/mobile/src/lib/chat-storage.ts.
    • 
      
  • Sidebar and nav: apps/web/components/dashboard/sidebar.tsx, sidebar-nav.tsx (APP_NAV_ITEMS), phone drawer in mobile-nav.tsx. Directions 2 and 3 add rows or sub-rows here.
    • 
      
  • The server record every direction reads: apps/web/agent/hooks/persist-conversation.ts → apps/web/lib/conversation-log.ts; threading in apps/web/lib/conversation-continuity/ (episodes, deliveries, open loops); web deliveries in apps/web/agent/hooks/continuity-web-delivery.ts. Channel adapters feeding the same record: apps/web/agent/channels/telnyx.ts (SMS) and apps/web/agent/channels/email.ts (email replies via Resend inbound, reply-to homa@mail.thankshoma.com). Tables: supabase/migrations/20260709121000_conversation_messages.sql, 20260711143707_conversation_continuity.sql.
    • 
      
  • Memory and context: apps/web/lib/learning/save-memory.ts, apps/web/agent/tools/recall.ts, apps/web/agent/instructions/family-context.ts.
    • 
      
  • Policy: the one-thread ruling lives in the build log (2026-07-10 evening) and the founder-ruling register (docs/homa-planning/journeys/10-reconciliation.md §5). A direction 2 or 3 winner requires a ruling update there, logged in docs/homa-planning/build-log.md.
    • 
    

    
Reuse versus new: direction 1 is M1-02 (Postgres becomes the render source) plus an in-thread search over existing RLS-readable rows; no schema change. Direction 2 needs episode titles (new column or projection: a schema decision), a scoped transcript read, and a sidebar list; it also re-opens the composer-scoping question. Direction 3 needs a read-only day-page projection over existing rows plus a "pick this back up" context injection (the continuity context pattern already exists). Direction 4 is the smallest: open loops are already tracked; it needs loop chips above the composer and a catch-up prompt. Every new read path goes through the isolation guard (pnpm check:isolation) before shipping.
