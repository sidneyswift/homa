Why this exists

Alessa asked Homa to research a curriculum, learn everything about it, and build a full 36-week program. Homa drafted a 7-block scope, then said she could not build all 36 weeks in one sitting, and called no tool. That is not a model weakness, it is agent/instructions.md lines 191-199 doing exactly what it was written to do: "everything happens this turn, or not at all... set it up as real scheduled work with create_task." create_task only builds recurring reminders (weekdays + hour); it has no idea of a finite job that runs its stages once and stops.

The curriculum request is the trigger, not the boundary. The Mac mini's real advantage was never "she can build curricula," it was a handful of unrestricted tools (shell, file read/write) plus a library of skills, which let her take on any long job a skill could describe. The first version of this plan built a job primitive that only curriculum-studio could use, named after curriculums in the schema itself. That was scoped too narrowly. This revision generalizes the job/stage tables so any current or future fleet skill (a multi-session research report, a photo-sorting project, a whole unit study, whatever comes next) can start, checkpoint, and resume a long job through the same primitive. Curriculum studio is the first skill that uses it, not the reason it exists.

Expert council review · 2026-07-18

Three-expert council verdict, folded into this revision

A council of three experts (Vercel platform July 2026, long-running-agent UX, modular systems architecture) independently reviewed this plan, cross-examined each other's reviews, and a moderator consolidated the verdict. All three ruled ship with changes. Every blocking and important change is already folded into the sections below; this card is the receipt.

The one blocking factual kill: the original A4 mechanism ("add @workflow/core as an app dependency") collides with eve, verified in eve 0.19.0's shipped build output, which claims the .well-known/workflow/ route namespace for itself. The app-facing SDK would generate routes into a namespace eve already owns, against the same project-scoped backend, on a mismatched beta protocol. No supported two-runtime story exists. A4 is now a Postgres claim-lease runner reusing the claimDueFamilyTasks idiom; the council chose not even to spend a spike on the old path.

Council consensus adopted throughout: a typed JOB_CONTRACTS registry with pnpm check:jobs (modularity), a frozen four-verb tool surface adding respond_to_agent_job for steering (agent-ux), the agent_job_events timeline table plus job.* analytics events in stage 1 (agent-ux + modularity), the artifacts side table replacing material_id (modularity), server-side one-active-job dedupe returning a success-shaped "already running" result (agent-ux), the hardened WorkerBrief/WorkerResult worker envelope with the crawl bound enforced as a sandbox egress firewall rather than tool-code convention (modularity + vercel), Homa's own awareness of her jobs via family context and checkpoint cards (agent-ux), and gate-first-volume as the approval model (all three, after vercel withdrew gate-every-volume).

Verified platform facts that shaped it: Vercel Workflows is GA with unlimited sleep but only 7-day Pro retention after completion (so our tables are the audit surface either way); Vercel Sandbox has deny-all egress with per-domain allowlists, credential brokering, live policy updates, and sub-second p75 snapshot restores; a full 36-stage build costs roughly $0.40-0.80 of sandbox time. The moderator settled one factual dispute by re-reading eve's route-normalization source: the namespace claim is real, though protocol traffic redirects into /eve/__server only for /eve/v1 routes.

Council's best net-new ideas, not yet scheduled: a "while you slept" morning-brief section fed by agent_job_events (~1-2 days, every future skill inherits it); the Binder filling in live as stages render, so pause/cancel feels safe because nothing built is hostage (~2-3 days); and the between-checkpoint heartbeat line ("drafting week 11, started 20 minutes ago"), deliberately not a token stream, nearly free once the events table exists.

A0. How much computer does Homa get, and where does the wall sit? RESOLVED · isolated worker

Decided 2026-07-18: the isolated worker, not root bash. Homa gets full code-execution capability through a declared, family-context-free worker subagent (detailed below and built in stage 6), and root Homa keeps its bash/write_file sentinels in place. This is the council's unanimous pick, and it is the option that does NOT reverse the 2026-07-09 security ruling, so no founder-ruling-register change is needed; the existing posture stands and the capability arrives beside it. The crawl-scope question below is folded into the same decision: the bound stays, but it moves from tool-code convention into the sandbox egress firewall (per-job allowlist, widenable live on approval), so it is a firewall policy, not a hard-coded ceiling.

The original open question, kept for the record: should root Homa get code execution (write files, run a shell) the way Mac-mini Homa does, and should the web-sourced ingestion path (A3 below) drop its same-origin crawl bound along with the per-family daily budget already removed from web_fetch.ts. Both were genuine security tradeoffs. The resolution above answers both.

The Mac mini and the cloud fleet do not share a trust model. docs/homa-planning/15-agentic-architecture.md §4 says this in as many words: the Mac mini has "no tenancy walls, one family, full trust"; the cloud "pays for multi-tenancy with RLS, scanned writes, budgets, and model mix." bash and write_file are disabled for root Homa today by an explicit founder ruling (2026-07-09, §3 of that doc), re-verified twice since: a live probe showed the model never even attempts bash unprompted, and a separate finding (F11, the create_printable render path, already fixed in commit 6c6c380) showed exactly how untrusted content can turn one privileged tool into a leak across every family sharing that runtime. A shell or arbitrary file write on ROOT Homa is not "one family's risk" the way it is on a Mac mini, it is every family's risk at once, because one turn, for one family, runs in the same privileged context that holds every family's live data access.
Recommended: an isolated worker, not root access

Bring the already-agreed "Stage 4" forward: one declared subagent authored closed, its own tools/ (shell, file write, browser, whatever a skill needs), its own deny-all-by-default sandbox.ts, no family context passed in at all, a bounded typed output back to root Homa. Root Homa never runs code directly; a skill hands the worker a scoped, written brief and gets a typed result back. This is a stronger answer to "Homa should be able to write code" than giving root Homa a shell: the worker can genuinely do anything a skill asks (write and run a script, drive a browser, OCR a document) precisely because it never carries a family's database credentials, so a bad turn there cannot reach another family's data even in the worst case.

~1 week, closes the capability gap without the blast radius
Alternative: give root Homa bash/write_file directly

Delete the two sentinel files (agent/tools/bash.ts, agent/tools/write_file.ts) and reverse the 2026-07-09 ruling outright. Fastest path to "just like the Mac mini." Every family's turn now runs with shell and file-write access in the one process that also holds every other family's data through the same session mechanics; an injected prompt from a fetched page or an uploaded file has a materially larger blast radius than today.

~1 day, reverses a named security ruling fleet-wide

The root-bash alternative above was weighed and declined on 2026-07-18 (see the resolved banner at the top of A0). Kept here so the tradeoff that was considered stays legible.

Web crawl scope, separately from cost. The per-family daily web_fetch budget is already gone (paywall/credits handle cost, not a hard ceiling). The same-origin, first-page-only crawl bound proposed in A3 is a different thing: not a cost brake, an injection boundary. It exists so a page that tells Homa "now fetch these forty other links, including this one that isn't even on this site" cannot turn one web_fetch call into an unbounded crawl across arbitrary hosts chosen by whatever text was on the page Homa just read.

Recommended: keep a bound, make it generous

Same-origin by default, but raise the depth from 1 page to a real crawl (e.g. up to 20 pages, following links found on already-fetched pages of the same site) so a real curriculum's scope-and-sequence, spread across several publisher pages, actually gets read. Off-site links found on a page are surfaced to the model as candidates, never auto-followed.

Still no cost cap, only a same-origin fence
Alternative: no bound at all

Any link on any fetched page can be followed, any host. Genuinely closer to what a Mac mini's curl/browser could do. Removes the one structural defense this tool has against a page instructing Homa to go fetch and relay content from somewhere else entirely.

Reopens the exact class of risk F11 closed on the render side

Resolved 2026-07-18: keep the bound, enforced as the sandbox egress firewall (per-job allowlist, widenable live on approval), not a hard-coded ceiling. The no-bound alternative was declined.

A1. The job schema, generalized

An untracked migration for a curriculum-only version of this already exists on disk.
found, not written by this plan

supabase/migrations/20260718120000_curriculum_jobs.sql is sitting in your working tree right now, uncommitted and unapplied. It was produced as a side effect of the research workflow that fed the first version of this plan (an agent I asked to design a schema wrote the file instead of only describing it, an overreach I did not intend), so treat it as a strong first draft, not an approved decision. It named everything after curriculums (curriculum_jobs, curriculum_job_weeks, curriculum_key); the schema below generalizes it into a shared job/stage primitive any skill can use, with curriculum-specific detail moved into the skill-owned plan/payload jsonb rather than baked into dedicated columns. Independently, the same "dedicated tables, not an extension of agent_schedules/homa_task_runs" conclusion was reached by a separate research pass reading lib/tasks/store.ts and both migrations for those tables.

Why not extend agent_schedules or homa_task_runs? agent_schedules is a pure recurrence engine (next_run_at, weekdays, lease_until); its kind check is deliberately closed and its claim/lease/advance loop exists only to compute "when does this fire again," which a finite job never needs. homa_task_runs is a good one-row-per-send audit/outbox, but its 2-hour stale-run reaper and its (schedule_id, scheduled_for) outbox uniqueness are tuned for a single dispatched turn, not a job that stays "running" for days and needs live pause/cancel. Widening either would force recurrence-shaped or single-shot-shaped code to special-case a row that is neither. 
create table if not exists public.agent_jobs (
  id uuid primary key default gen_random_uuid(),
  family_id uuid not null references public.families (id) on delete cascade,
  child_id uuid references public.children (id) on delete set null,
  requested_by_user_id uuid references auth.users (id) on delete set null,
  session_id text,                      -- audit pointer only, never load-bearing
  skill text not null,                  -- closed set, validated against JOB_CONTRACTS
  title text not null,
  plan jsonb not null default '{}'::jsonb,   -- shape owned by the skill's zod contract
  plan_revision smallint not null default 1, -- bumped only by the runner, with plan, in one tx
  total_stages smallint not null check (total_stages between 1 and 200),
  current_stage smallint not null default 0,
  status text not null default 'queued'
    check (status in ('queued','running','paused','awaiting_input',
                       'completed','cancelled','failed')),
  progress_note text,                   -- derived one-liner; agent_job_events is the real feed
  start_idempotency_key text,           -- verbatim-retry guard only, not the dedupe
  cancel_requested_at timestamptz,
  cancelled_at timestamptz,
  completion_task_run_id uuid,          -- composite FK below, council-confirmed fix
  ...
  foreign key (completion_task_run_id, family_id)
    references public.homa_task_runs (id, family_id)
);

-- THE dedupe (council: server-side constraint, not the model-supplied key):
-- at most one live job per family+skill+child. On conflict, start_agent_job
-- returns a SUCCESS-shaped result carrying the existing job's status and
-- steering options ("this build is already running, volume 3 of 9").
create unique index agent_jobs_one_active_idx
  on public.agent_jobs (family_id, skill, coalesce(child_id, '00000000-...'::uuid))
  where status in ('queued','running','paused','awaiting_input');

create table if not exists public.agent_job_stages (
  id uuid primary key default gen_random_uuid(),
  job_id uuid not null references public.agent_jobs (id) on delete cascade,
  family_id uuid not null references public.families (id) on delete cascade,
  stage_number smallint not null,
  status text not null default 'pending'
    check (status in ('pending','in_progress','ready_for_review',
                       'approved','superseded','skipped','failed')),
  title text,
  payload jsonb not null default '{}'::jsonb,  -- shape owned by the skill's zod contract
  -- Billing truth (council tiebreak): typed, SUM-able columns the paywall/credits
  -- code queries directly, never parsed out of jsonb.
  sandbox_cpu_seconds numeric,
  page_fetch_count smallint,
  model_tokens integer,
  ...
  unique (job_id, stage_number),
  foreign key (job_id, family_id) references public.agent_jobs (id, family_id)
);

-- Artifacts are a side table, NOT a material_id column on the stage row
-- (council: many artifacts per stage, provable tenant coherence per kind,
-- and a new artifact kind later is one additive nullable column here).
create table if not exists public.agent_job_stage_artifacts (
  id uuid primary key default gen_random_uuid(),
  stage_id uuid not null references public.agent_job_stages (id) on delete cascade,
  job_id uuid not null,
  family_id uuid not null references public.families (id) on delete cascade,
  kind text not null check (kind in ('material')),  -- widens additively per kind
  material_id uuid,
  created_at timestamptz not null default now(),
  check ((kind = 'material') = (material_id is not null)),
  foreign key (job_id, family_id) references public.agent_jobs (id, family_id),
  foreign key (material_id, family_id) references public.materials (id, family_id)
);

-- The parent-visible timeline and the runner's own audit trail. Progress UI,
-- morning brief, ETAs, and actor attribution all read THIS, not progress_note.
create table if not exists public.agent_job_events (
  id uuid primary key default gen_random_uuid(),
  job_id uuid not null,
  family_id uuid not null references public.families (id) on delete cascade,
  stage_number smallint,
  kind text not null check (kind in ('stage_started','stage_completed',
    'milestone','steering_applied','error','eta_updated')),
  actor_user_id uuid references auth.users (id) on delete set null,
  payload jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now(),
  foreign key (job_id, family_id) references public.agent_jobs (id, family_id)
);

What makes this general (council-confirmed), and the rules that keep it so:

  • JOB_CONTRACTS registry, shipped WITH the first migration: a typed zod contract per skill (plan, stagePayload, respond-arm unions, WorkerBrief/WorkerResult, plus describeStage for generic status rendering), the same pattern as packages/core/src/events.ts. start_agent_job validates the skill against the closed key set and parses the plan before insert; the runner parses every stage payload. A new pnpm check:jobs guard mirrors check:events in CI. This is what makes skills #2 and #3 zero-migration: jsonb alone would be the classic unqueryable-everything trap.
  • Plan amendments never rewrite history: a mid-job scope change ("make week 5 about dinosaurs") bumps plan_revision, marks affected pending stages superseded, and re-expands from the revised plan. Approved stages are never silently rebuilt. total_stages is revisable only by the runner's service path, in the same transaction, never below current_stage.
  • Jobs cannot breed jobs: extend the refuseScheduleSpawnedSession idiom (lib/tasks/guard.ts) so worker-spawned sessions refuse start_agent_job.
  • Both event layers ship in stage 1, not later: the agent_job_events product table above, plus content-free generic job.* analytics events (job.started/stage_completed/ completed/cancelled/failed, skill as a prop) in EVENT_SCHEMAS, satisfying the MJ-08 law up front.

A4. How stages actually run (rewritten after the expert council)

The council killed this plan's original mechanism with a verified in-repo fact. The first draft said "add @workflow/core as an explicit apps/web dependency and run the stage loop in a new Vercel Workflow." The Vercel-platform expert verified that eve 0.19.0 ships a vendored, compiled copy of @workflow/core and its build output claims the workflow route namespace for itself: EVE_VERCEL_FUNCTION_PREFIXES = ['eve/', '.well-known/workflow/'] in eve-service-route-output.js (moderator re-verified in this repo). The app-facing SDK (the workflow package plus withWorkflow(), not @workflow/core, which apps never install) generates its own app/.well-known/workflow/ routes at build, into a namespace eve already owns, backed by the same project-scoped managed backend on a different beta protocol version. No supported two-runtimes-in-one-deployment story exists anywhere in Vercel's docs. This is a route-ownership collision, not a version nuisance.

What the plan does instead (unanimous council consensus): a Postgres-native claim-lease stage runner, the same idiom claimDueFamilyTasks already uses in lib/tasks/store.ts:189 (atomic for update skip locked lease on the row). The runner claims the next runnable stage, executes it in one Fluid invocation, upserts the stage row, and repeats, driven by the existing cron cadence (or a Queues topic later). Parent-facing messages fire only at real milestones. Nothing reuses or edits channels/dispatch.ts.

The dumb-orchestrator invariant (binding, substrate-neutral). Only Postgres holds job or stage content between stage boundaries. The runner transports IDs, re-reads rows at every boundary, and cancel/pause/approve are decided solely by row state. If the orchestration substrate ever changes (a separate-project Vercel Workflow for observability is the documented future upgrade), the state machine does not move.

Multi-day pauses are fine on this substrate: a job in awaiting_input is just a row no claim predicate picks up; it costs nothing and waits indefinitely. The council also verified Vercel Workflow's own numbers (GA, unlimited sleep, suspended runs cost ~$0.02/1K events) for the future separate-project path, but its post-completion retention is only 7 days on Pro, so the product's audit surface must be our own tables either way.

Alternatives considered and rejected

In-app Vercel Workflow: the namespace collision above; council tiebreak was to not even spend a build stage spiking it. Instead, extend scripts/eve-upgrade-check.mjs (~0.5 day) to diff eve's @workflow pins and its route-prefix claim on every eve bump, and fail CI if apps/web ever gains a workflow dependency without a recorded founder decision. Eve-session piggybacking: still blocked on M1-15 (unbuilt session rotation) and the "nothing load-bearing in session history" doctrine. channels/dispatch.ts reuse: still wrong, its message.completed handler would SMS the parent Homa's raw drafting reply after every stage.

A5. The instructions.md carve-out

The current binding law (lines 191-199) has one sentence that needs a precise amendment, or the model will keep treating create_task as its only escape hatch:

Proposed addition, placed right after the existing "set it up as real scheduled work with create_task" sentence, worded generically so any skill can rely on it, not just curriculum-studio:

A6. The skill fleet that rides this primitive add skills

This is the payoff of building a general job primitive instead of a curriculum feature: each new long-running capability is one SKILL.md plus one typed JOB_CONTRACTS entry, with no migration and no change to the generic job infra. This is the modularity a Mac mini gets from "a couple tools and a bunch of skills", now delivered inside the tenancy walls. Curriculum-studio is the first consumer and ships with the primitive; the three below are independent follow-on consumers, each provable in isolation.

curriculum-studio (the anchor, ships in v1)

Build a multi-week curriculum for one child. plan = { curriculumKey?, weeks, scopeAndSequence }; stagePayload = one week's focus + activities. Artifact kind: material (packet). The proving consumer for the whole primitive.

already in the build order
unit-study-builder

A themed cross-subject unit over several weeks, for one child or all of them ("a 6-week ocean unit"). plan = { theme, subjects[], weeks, children[] }; stagePayload = one week's cross-subject activities. Artifact kind: material. The cleanest zero-migration proof, it reuses create_printable exactly like curriculum-studio.

~2-3 days, no migration, no new artifact kind
portfolio-compiler

Assemble a compliance portfolio from the family's existing stored materials, logged hours, and progress readings, a real legal requirement in portfolio-review states. plan = { child, term, subjects[] }; stagePayload = one subject's evidence gather + layout. Artifact kind: material (packet). No web, no fresh generation, lowest risk, proves the primitive serves a compile-from-stored-data job, not just generation.

~3-4 days, no migration, no web/worker needed
topic-deep-dive

"Learn everything about [X] and give me a teaching plan", literally Alessa's original ask, now a real job. Stages: search → read sources in the worker behind the firewall → synthesize → brief. plan = { topic, angle }; stagePayload = one source read or one synthesis pass. This one adds a new artifact kind (report), the one additive nullable column the plan already flagged as the artifact-table seam. Extends, does not replace, the daily research-brief skill (the long-job sibling of the one-note morning brief).

~4-5 days, +1 nullable artifact-kind column, exercises the worker
Why this is cheap and safe (the modularity claim, made concrete). Adding a skill touches only apps/web/agent/skills/<name>/SKILL.md, a new zod entry in lib/jobs/contracts.ts, routing fixtures, and pnpm check:fleet-skills. Skills 2 and 3 need zero migration; topic-deep-dive adds one nullable artifact_kind value, exactly the seam A1 named. Count check: active fleet skills go from 2 today (materials-studio, research-brief) to about 6; that is still all-advertised static routing, far below the 25-40 that would reopen dynamic distribution (filesystem-first ruling, 2026-07-15). Sequencing: curriculum-studio ships in v1 to prove the primitive; the other three land after the primitive is stable in production, each independently, so any one can be dropped or reordered without touching the infra (see tweak #3).

One honest caveat: a SKILL.md that calls start_agent_job cannot be written before that tool exists (stage 2). So these are specified now and built once the primitive is real, not scaffolded as dead code today. That is the correct order, not a delay.
