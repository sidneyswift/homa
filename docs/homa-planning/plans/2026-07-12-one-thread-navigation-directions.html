One thread. How does she move through it?

Round one picked a premise to explore deeper: ONE continuous conversation, identical on laptop and phone, with texts, emails, Homa's briefs, and task results all flowing into it. This round holds that premise constant and varies only the wayfinding: how she finds a past moment, what selecting it does, how she gets back to now, and what Homa is told. Four different bets, same fake week.

Every person, message, and record here is fake. No real family data is loaded. No product code or route was changed.

The core decision: with everything in one stream, is the way back through time a search box, a slide-out list of moments, a timeline you scrub, or Homa herself? And when she gets there: does she read, jump, or pick the conversation back up?

Wiring note (for the build after you choose)

    
No real application code was touched by this lab. Likely integration paths, verified in the repository:

    
    
      
  • The thread itself: apps/web/app/app/chat-client.tsx + transcript-days.ts render it today from the localStorage cache (chat-storage.ts); the merged thread makes Postgres the render source (M1-02) reading public.conversation_messages filtered per adult (ruling chat-privacy-per-adult, 2026-07-12): the caller's own member_user_id plus deliveries addressed to them, visibility = 'family' rows only, paginated by day. The current family-wide SELECT policy tightens to per-adult under M1-02 (expand-contract, isolation guard before and after); the recall tool's conversation arm gets the same filter. Mobile twins under apps/mobile/src/.
    • 
      
  • Channels already writing to that record: web (agent/hooks/persist-conversation.ts), SMS (agent/channels/telnyx.ts), email (agent/channels/email.ts), scheduled briefs (agent/schedules/dispatch.ts via the delivery ledger). Task results ride the same dispatch path; rendering them in-thread is a read decision, not a new write.
    • 
      
  • Pick-up context: lib/conversation-continuity/reply-policy.ts (renderContinuityContext) already builds the episode context block for cross-channel replies; a tap-driven pickup reuses it, carried in session auth attributes like continuityContext today. Recall for anything older: agent/tools/recall.ts.
    • 
      
  • Moments list (direction 2): episodes exist (public.conversation_episodes); titles do not. Auto-titling is a new column plus a cheap model pass, a schema decision. Days-only navigation (directions 1 and 3) needs no schema change.
    • 
      
  • Search (direction 1): conversation-scoped search can reuse the recall read path (FTS + semantic over conversation_messages) under the caller's own JWT; a full-record search across materials and memories is a bigger index decision (question 5).
    • 
      
  • Photos: texted images persist as caption text (lib/voice/caption-image.ts), so the merged thread shows captions, not images, until media storage exists. Flagged honestly in the mocks.
    • 
      
  • Policy: the one-thread ruling (build log 2026-07-10 evening) holds for directions 1, 3, 4; direction 2's panel needs a conscious ruling note. Founder-ruling index: docs/homa-planning/journeys/10-reconciliation.md §5.
    • 
      
  • Every new read path passes the isolation guard (pnpm check:isolation) before shipping.
    • 
    

    
Reuse versus new: directions 1 and 3 are read-path plus client work only. Direction 2 adds episode titles (schema) and the panel component. Direction 4 adds a navigation tool the agent can call (scroll targets from message ids) plus jump cards; its context story is pure reuse. The "what Homa sees" peek in any direction is a UI window onto the existing continuity context, no new plumbing.
