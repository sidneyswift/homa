The unknown unknowns you asked for

Six blind spots · what the dashboard cannot show until they are fixed

Each one is real, with the file or table that proves it. The dashed "not instrumented yet" tiles inside the directions come straight from this list.

High · silent loss

Report and reminder emails vanish without a trace

Onboarding-funnel email (report links, 24h reminders, retest nudges) goes out through apps/web/lib/map/email.ts, which returns submitted / rejected / unknown, and every caller logs it to the console only. Only dispatch-channel sends (journal, brief, custom tasks) land in conversation_deliveries. "Did emails get received" is unanswerable for half your email today.

Close it: Resend webhooks (delivered / bounced) into a ledger, or write map sends into conversation_deliveries too.

High · money

Billing truth lives in Stripe, not in your database

There is no Stripe webhook handler. families.trial_started_at is stamped only when the parent lands back on /api/billing/confirm; a closed tab after payment leaves money in Stripe and nothing in Postgres. Paying-family and MRR tiles cannot be trusted from the DB alone.

Close it: the M1-06 webhook (checkout.completed, subscription.updated), or a nightly Stripe API pull into a local table.

Medium · false signal

families.status lies about "where they're at"

The enum (open, complete, claimed, deleted) exists but app code almost never writes it. Lifecycle stage must be derived: account (auth.users) → setup (profile_completed_at) → kids (children rows) → report (child_reports.generated_at) → trial (trial_started_at) → active (recent conversation_messages).

Close it: one SQL view (family_stage) computed from those timestamps, so every surface agrees.

Medium · scary bucket

"Uncertain" is a first-class delivery state, not an edge case

homa_task_runs.status includes partial_uncertain and uncertain; conversation_deliveries.status includes uncertain (a send with no provider receipt). A sent/failed binary quietly hides the bucket where you genuinely do not know whether a mom got her text.

Close it: render three outcomes everywhere (sent · failed · uncertain) and treat a growing uncertain count as its own alert.

Medium · dead man's switch

The hourly cron has no heartbeat

vercel.json fires /api/map/cron hourly (reminders, retests, transcript sync, thank-you cards). Failures are console + HTTP 500, kept only in Vercel logs. A dead cron looks identical to a healthy quiet one. homa_task_runs covers the eve dispatcher, not this route.

Close it: a cron_runs row per tick (job, counts, error), and the dashboard alarms on a missing hour.

Low · wrong proxy

Logins are not activity, and cost is already measurable

Sessions persist, so auth.users.last_sign_in_at barely moves; "active" must come from conversation_messages and events, not logins. Meanwhile model_usage already records per-family AI spend per call, and the margin law (P50 under $10 per family per month, journeys/06 §3) is checkable today; nobody is looking at it.

Close it: define "active = any message or evidence event", and put the cost percentile tile on the default view.

Build-changing questions

Five decisions that change routes, schema, or wiring

1 · Where does the console live?

Inside the deployment means one codebase and instant mapDb() access, but the gate must be airtight. A separate app isolates risk and adds a second deploy to babysit. Saved SQL is zero build but no alerts, no drill-down.

2 · How is it locked to you?

An env allowlist of founder user ids checked in the server layout is smallest and needs no migration. A role column is cleaner long-term but touches schema (isolation guard, RLS review). A secret URL is weakest, held only by obscurity.

3 · MJ-14 promises 5 wake-up alerts. What is v0?

Dashboard-only means you find failures when you look. A 7am email digest costs one cron job. SMS-to-you within the hour needs a Telnyx self-notify path but matches the "a new family is standing in her kitchen right now" alert philosophy in journeys/06 §5.

4 · Which blind spot gets closed first? (pick up to 2)

Each is a small schema or webhook addition; ordering decides what the v0 dashboard can honestly display versus what stays a dashed ghost tile.

5 · Live queries or rollups?

Live SQL on page load is honest and fine at n under 100 families, but history (sparklines, week-over-week) only exists if something snapshots it. Nightly rollup rows cost one job and give you trends forever.
