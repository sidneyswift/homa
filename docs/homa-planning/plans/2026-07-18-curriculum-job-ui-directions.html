Build-changing questions

1. Per-child or family-level scope?

Per-child (like Planner/Binder) needs a child_id column and every route re-scoped by the view-context cookie. Family-level (like Tasks) needs no new scoping mechanism, but two kids' builds only separate by name in card copy, not truly.

2. A new nav item, or folded into an existing tab?

The sidebar's nav list has no precedent anywhere in this codebase for a conditionally shown item. A 6th item costs permanent IA for every family, even those who never build a curriculum; folding into Tasks costs zero nav changes.

3. Blocking approval gate per volume, or fire-and-forget with only cancel?

A gate needs the Workflow to durably suspend on "awaiting_input" and a resume action. Fire-and-forget needs none of that, but risks generating all 36 weeks on an unconfirmed assumption, the same failure mode that already burned Alessa once.

4. Who can approve, pause, or cancel?

Tasks today draw no distinction; any family member can pause any task. A 36-week build is a bigger, costlier action to let a co-parent silently redirect or cancel. A real RLS/permissions decision, not just copy.

5. Does partial output stay visible if paused or cancelled?

Visible-as-you-go means each week's artifact renders into the Binder the moment it finishes, a progressive-reveal pattern no artifact type has today. Hide-until-done is simpler, but throws away real, already-generated work the moment a parent pauses to think.
