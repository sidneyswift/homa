# Deeper questions that follow the child's evidence

Implementation and evidence for [#1088](https://github.com/sidneyswift/homa/issues/1088), F09-F10 in the [meeting review](2026-09-05-cofounder-feedback-review.md). Not yet deployed or live-certified. GitHub holds status and ownership.

## What the request means

Carolyng wanted questions that reveal what her child can currently do, including abilities above or below the age warm-up. Eight questions is a sitting limit, not the outcome or proof of a precise ability age. The meeting did not request an automatic practice-plan rebuild or assessment schedule.

The audit established two distinct failures. Returning-family deep links lost the selected child and subject on the way to chat. The chat check-in used the ordinary age warm-up window, so a saved catching or pouring answer could finish the sitting while useful questions remained elsewhere in the bank. The older dedicated deep-dive selector explored more widely but did not refresh stale evidence and automatically rebuilt a plan. Restoring it unchanged would not satisfy this request.

## Current implementation

The fleet `progress-check-in` skill owns reading evidence, asking the exact selected question, conservative interpretation, tool sequencing and the explanation at completion. Existing `manage_child_progress` owns the authenticated effect. The new deterministic subject selector uses the reviewed bank and canonical effective evidence, with family/child-scoped skip cooldowns. It probes easier or harder questions, refreshes stale or non-direct controlling observations, excludes fresh answers and bounds the sitting to eight accepted responses including skip and not_sure. Ordinary onboarding keeps its age warm-up selector.

The selector returns a question or a typed stop reason. A sitting limit, bank coverage limit, no useful question and parent stop remain distinct. Mixed evidence about different skills does not imply that the bank ended or that the child has one precise level. The scorer and evidence freshness policy are unchanged: freshness guides question selection, not score decay.

The selected web action carries a validated child, subject and request ID through authentication, account setup, chat readiness, queueing and retry. The server re-scopes the child to authenticated family membership and rejects altered selected scope before Eve dispatch. The start receipt is atomic with start, resume or no-question outcome. A different subject, purpose or adult cannot silently take over the current sitting.

Answers require a real bound current delivery. The audit of this implementation found an existing null/null comparison that could accept an answer before a question was delivered; that shared guard is corrected for every check-in purpose. Accepted answers produce response/evidence/projection updates in the existing transaction. A legitimate saved answer can leave the score unchanged. Completion returns the exact child's selected Progress subject, without starting a plan or another sitting.

## Recovery and delivery corrections

A fresh technical review caught two blockers in the initial implementation, preserved at `090849e0`. Correction `bd6db5d0` added recovery and native literal delivery checks; local integration `3cb8bf67` also contains main `ff3258bf`. Its fresh review reproduced two remaining failures: separate receipt/sitting reads could combine different revisions, and web could bind a completed apology after a committed tool timed out. Correction `9e16b1f4` addressed both. Its review then reproduced an ordinary-chat reissue that advanced the sitting without its undelivered selected receipt. The current correction carries that receipt forward atomically and makes an unexplained active, unbound revision mismatch unavailable instead of terminal.

1. An accepted start was initially treated as a delivered question. Now the start result remains immutable while separate issued-revision and delivery fields record whether its question arrived. Passive reload reads status without sending again. Explicit retry can reissue only the same active, unbound question for the same adult and revision. It preserves the sitting/item, increments the revision and binds the new turn. An ordinary chat reissue of that same undelivered question now moves every matching selected receipt in the shared transaction, so another failed delivery remains recoverable with the new revision. Late old-turn delivery, raced retries, advanced answers, parent pauses, changed owners and terminal sittings cannot restart the original action. Successful delivery stamps the receipt in the binding transaction. Status now reads receipt and sitting through one PostgreSQL view with `security_invoker = true`, so one statement snapshot and the caller's underlying RLS govern the whole result. An unexplained same-owner active, unbound revision mismatch keeps the recovery pointer without authorizing a retry; aligned receipt lineage is required before retry can proceed.
2. A matching pending turn does not prove a question card was emitted: a tool can commit and then time out before returning its result. Both web and native text must contain the exact selected statement. The shared binder enforces this against actual canonical persisted content, including its 8,000-character limit; the runtime/turn marker separately ties that statement to the current revision. A card-only apology or a raw event containing a statement beyond that limit is insufficient. The fleet procedure already requires the exact statement for all check-in purposes. Onboarding's full-screen checklist has its separate delivery path. The native voice bridge stays excluded from this newly enabled native-text path.

The additive migration records exact terminal metadata and creates adult-owned start receipts with RLS read access and no browser writes. Legacy outcomes keep unknown reason/counts. Root owns production migration ordering and deployment verification.

## Final integration gate

Integration with main `b8b79693` passed the independent technical review, preview deployment, browser and database CI jobs. The first required aggregate failed because the isolation guard did not yet enumerate the new receipt table. The guard now probes both the table and status view, refuses a partial migration, and explicitly labels the pre-migration absent state. Once installed, real JWT probes cover the owning adult, another adult in the same family, another family, and all client write methods. Catalog checks separately prove member SELECT only and no anonymous access.

The updated disposable PostgreSQL contract passed for both relations: owner reads one receipt, partner/outsider read none, anonymous SELECT is denied, and every member write is rejected. Its first new run exposed a test expectation error: PostgreSQL can reject the joined view as non-updatable before evaluating permissions. The corrected assertion accepts that exact view-only SQLSTATE after separately checking revoked write privileges. The REST probe submits only columns actually present in each relation, so an unknown-column error cannot pass as security evidence. Production migration and hosted acceptance remain pending.
