Background work · six directions, cheapest first

The ask: when a parent requests something slow (a worksheet build runs 60 to 113 seconds in the build log), could Homa spin the work off like Cursor spins up subagents, reply immediately, and deliver when it is done? This doc answers three questions: how would we do it, is it worth it, and how hard is it. Every claim below is bought with a file path from the repo as of Jul 13.

Read this first: eve subagents are real (Homa's agent has the built-in one enabled today), but in eve 0.19.0 the parent turn waits until every child finishes. Subagents are parallelism inside the wait, not an end to the wait. The actual "reply now, deliver later" machinery in this codebase is the dispatch rails the morning brief already rides. Most of what the Cursor screenshot shows is wiring, not building.

Is it worth it?
Yes, staged. The wait is your most-documented wound.

The chat client carries a 180s stall watchdog and 240s turn recovery sized for worksheet turns (chat-client.tsx:144-157), the build log records 94.6s and 113.5s turns where the phone gave up before the server finished, and the product NFR says p50 under 30s, p95 under 60s for request to card (journeys/04-feature-journeys.md:177). Worse: while a build runs, the WHOLE conversation is locked, because a message sent while busy only queues client-side until the turn ends (chat-send-policy.ts).

Easy or difficult?
Middle. The rails exist; the last mile does not.

A one-shot background agent run is 90% built: the tasks framework's outbox (homa_task_runs), the dispatch channel's proactive sessions, the delivery ledger, and the transcript merge that already folds delivered task results into web scrollback on reload. Genuinely new: a tool to enqueue work from chat, live surfacing into an open tab (no realtime or polling exists), and idempotency so a redelivered job cannot re-bill image generation.

Recommendation
1 and 2 now. 3 is the feature. 4 makes it feel magic.

Option 1 ships today and kills the "is it stuck?" panic. Option 3 (the background lane) is 2 to 4 focused days on proven rails. Option 4 (live arrival in the open tab) is what makes it feel like the Cursor demo. Skip real eve subagents (option 5) until multi-kid batch requests show up in usage. Option 6 is the full orchestrator and needs product rulings first.

The mental model: three lanes, two already paved

Today's web chat One blocking turn She sends, one durable eve session runs model + tools + render + review inline, the NDJSON stream feeds the tab, and the reply lands when everything finishes. 60 to 113s for materials. Composer queues anything she types until the turn ends. Files: agent/channels/eve.ts, agent/tools/create_printable.ts, app/app/chat-client.tsx.
Already paved The dispatch lane (morning brief, tasks) A claimed row in agent_schedules / homa_task_runs wakes a fresh agent session with no browser attached (agent/schedules/dispatch.ts). The channel persists the composed result to conversation_messages, delivers by SMS or email or saves it, and the web transcript merges it in on next load (lib/chat-history.ts:103-135). The tasks page even has a Run now button that starts one on demand (agent/channels/dispatch.ts:332-398). Tenancy: dispatch is a pinned channel in lib/agent-db.ts, and create_printable already handles pinned mode.
The missing mile Chat-initiated background + live arrival No tool lets the chat agent enqueue a one-shot background run. No realtime, polling, or push exists for the open chat tab, so a background result appears only after reload. History rows render as plain text, so a background-built worksheet would arrive without its preview card (lib/chat-history.ts:38 selects content only; MaterialCard renders from live tool parts).

Landmines found before writing any code

4 landmines · 2 unwritten conventions · 1 missing concept. Each one is bought with a file, and each card ends with the sentence to paste into the implementation prompt.

Landmine 1

Eve subagents do not free the turn: the parent blocks until every child returns

eve/docs/subagents.mdx says it plainly ("eve runs that batch concurrently and returns every result before the parent continues") and the types confirm it: a PendingRuntimeActionBatch holds the parent turn open for every subagent-call (eve/dist/src/harness/runtime-actions.d.ts). Asking the model to "spin up subagents" gives you a prettier 68 seconds, not a shorter one. The Cursor behavior in the screenshot (turn ends, work continues, notify later) maps to eve schedules plus cross-channel receive(), which resolves when the new session STARTS (agent/schedules/dispatch.ts:41-45).

Prompt fix: "Do not use eve's subagent tool for backgrounding. Start a separate durable session through a channel receive, dispatch-style, and let the chat turn end."
Landmine 2

You cannot inject a finished result into the live chat session

Eve keeps one active continuation per session and no durable inbound queue (eve/docs/concepts/execution-model-and-durability.md, "Message delivery and queueing"). A background job must not try to wake the parent's web session with its result. The paved path is exactly what dispatch does: persist the result as a canonical message (persistCanonicalMessage, lib/conversation-continuity/ledger.ts:181) plus a conversation_deliveries row, and let the transcript merge pick it up.

Prompt fix: "The background session writes its result through the continuity ledger and delivery ledger. Never send into the parent's live eve session."
Landmine 3

At-least-once redelivery would re-bill image generation

The dispatcher is deliberately at-least-once: a crash between receive and advance redelivers, and the homa_task_runs outbox row is the idempotency guard (agent/schedules/dispatch.ts:36-39). That guard dedupes per schedule per local day. A one-shot build job that redelivers would re-run generate_image (real money, 150s cap, 30/family/day is the only stop) and insert a second draft material. The 2026-07-12 HookConflictError incident (two of three per-kid briefs lost to one shared token) is the same class of bug from the other direction.

Prompt fix: "Give each background job an idempotency key and a claimed/running/done row before the session starts; a redelivered claim must observe the row and refuse to re-bill."
Landmine 4

Fan-out with the built-in agent tool would double-write the transcript ledger

The built-in agent tool is live on Homa today (only bash, write_file, web_fetch carry disableTool() sentinels), and a child copy inherits the parent's auth attributes. The persist hook writes every message.completed with a familyId and no channel filter (agent/hooks/persist-conversation.ts:56), and continuity-web-delivery.ts:27 only skips when attributes.channel is set, which web sessions never set. A child session's chatter would likely land in conversation_messages and the delivery ledger as if Homa said it to her. Unverified in practice because nothing prompts the model to delegate today; verify before any instructions change encourages fan-out.

Prompt fix: "Before encouraging the agent tool, prove in dev what child-session events do to persist-conversation and continuity-web-delivery, and add a subagent guard if they double-write."
Unwritten convention 1

Every proactive lane finishes its run row from the channel, never the starter

Both existing background lanes learned the same lesson: receive() resolves at session start, so the schedule handler cannot judge the outcome. The channel's own message.completed finishes the run (agent/channels/dispatch.ts:52-55, agent/channels/research.ts:12-16), and a reaper fails anything still running hours later (reapStaleTaskRuns, lib/tasks/store.ts). A new background lane that finishes its row anywhere else will fight the reaper and the alerts page.

Prompt fix: "Follow the dispatch division of labor: starter claims and starts, channel finishes, reaper cleans up."
Unwritten convention 2

Task-spawned sessions must not spawn tasks, and laws gate new billables

The M3-08 guard refuses schedule-spawned sessions access to task CRUD so tasks cannot breed tasks (lib/tasks/guard.ts). A background-work tool is a new door into the same loop: a background session that can enqueue background sessions is a runaway. Separately, BUILD.md law #3 requires the typed event registry and the action-cost registry before a billable capability ships, and law #5's D4 floor applies if child photos ride into background builds.

Prompt fix: "Extend refuseScheduleSpawnedSession (or a sibling guard) so background sessions cannot enqueue more background work, and register events plus action costs before enabling the flag."
Missing concept

"Delivered to web" exists in the ledger but has no live doorway or rich rendering

The continuity system already models web as a delivery channel (recordReactiveDelivery with channel "web") and the transcript merge already folds delivered rows in on load. What does not exist: any way for an open tab to learn about a new row (no Supabase realtime anywhere in the app, no polling loop for history), and any way for a history row to render as a material card (rows carry only text columns, lib/chat-history.ts:38; cards render from live tool parts, message-parts.tsx:129-139). The report pages solved the same shape with a status poll plus self-heal (api/map/narrative-status/route.ts:55), which is the in-repo precedent to copy.

Prompt fix: "Treat live web arrival as its own slice with its own verification: a pending-job poll (narrative-status pattern) before any realtime bet, and a material reference on the delivered message so the card can render from the materials table."

The ladder: six places to intervene

Ordered strictly cheapest to most ambitious. Check what resonates; the assembler at the bottom writes your reply.

1

Warm words while she waits

S · ship today

Two tiny changes, no architecture. First, an instructions line: on web, before a material build, say one short sentence first ("On it. Skye's counting page needs a minute or two."), the same move send_heads_up already mandates on SMS. Eve streams interim text mid-turn, so the sentence appears immediately. Second, fix the busy label: busyLabel() returns "thinking…" for reasoning parts and tool gaps (message-parts.tsx:368-383), which is exactly the 68s screenshot; reasoning-aware labels ("designing the page…") close the panic gap.

Found in codeagent/instructions.md:132 already does this for SMS only; send_heads_up.ts:29 says web "sees progress live", which is true only when a tool is actively executing.
ImpactKills "is it working? is it not working?" (the 2026-07-07 tester memo panic) for every slow turn, materials or not. Does not shorten the wait.
Filesagent/instructions.md, apps/web/app/app/message-parts.tsx
2

Make "you can keep typing" visible

S

The composer already queues a message sent while Homa works and delivers it the moment the turn ends (chat-client.tsx:99-104, chat-send-policy.ts). But nothing tells her that. A quiet "will send when Homa finishes" chip on the queued message turns a hidden mechanism into permission to keep talking. Pure UI, zero server change.

Found in codeThe queue exists and is tested (chat-send-policy.test.ts); it just renders nothing while holding her message.
ImpactSoftens the conversation lock during long turns without touching the turn itself.
Filesapps/web/app/app/chat-client.tsx
3

The background build lane

L · the real feature

A new work_in_background tool, web and SMS chat only, behind a flag. It writes a one-shot job row (idempotency key, claimed state), starts a fresh dispatch-style session via the channel's receive (the Run now route already does exactly this, minus the tool doorway: agent/channels/dispatch.ts:332-398), and returns immediately so the chat agent can answer "I'm building it now, it will land in your binder and here in chat in a couple of minutes." The background session builds with the same studio tools under pinned-family tenancy, persists the result through the continuity ledger, delivers by SMS when linked, and the transcript merge already surfaces it on web at next load. The material itself appears in the binder regardless.

Found in codeOutbox + lease + reaper: lib/tasks/store.ts. Proactive session + delivery + run finishing: agent/channels/dispatch.ts. Web scrollback merge of delivered results: lib/chat-history.ts:103-135. Pinned tenancy for tool writes: lib/agent-db.ts.
New workThe tool, a background job kind (or schedule-less run rows), the loop guard, idempotent billing, action-cost + event registry entries, agent guidance for when to offer backgrounding (she chooses, offers never commands).
ImpactThe 60 to 113s turns become a 5 to 10s ack. The conversation unlocks. SMS families already live this shape; web catches up.
Watch outLandmines 2, 3, and both conventions above. V1 web arrival is reload-based; that honesty belongs in the agent's promise ("it will be here next time you look, or I can text you").
4

Live arrival in the open tab

M · needs option 3

The magic beat: she keeps chatting, and the finished worksheet card slides into the transcript by itself. Cheapest honest version copies the report pages' poll pattern (narrative-status): while this family has a pending background job, the chat page polls a small status endpoint every 10 to 15s; when the job flips done, fold the delivered message in and render the material card by fetching the materials row (store the material id on the job or delivery row). Supabase realtime is the fancier alternative, but it is a net-new dependency for the app; the poll costs nothing new and stops when no job is pending.

Found in codePoll + self-heal precedent: api/map/narrative-status/route.ts:53-68. Job state to poll: homa_task_runs (the tasks page reads it already). Card renderer: app/app/material-card.tsx.
ImpactThis is the difference between "background jobs exist" and the demo moment in the Cursor screenshot. Also fixes proactive briefs silently waiting for a reload today.
Filesapp/app/chat-client.tsx, one new status route, lib/chat-history.ts (material reference on delivered rows)
5

Parallel fan-out for multi-kid batches

M · only if batches are real

The one place true eve subagents earn their keep: "make a worksheet for all three kids" currently runs three builds serially inside one turn. The built-in agent tool (already enabled, never mentioned in instructions) can fan the three builds out concurrently, cutting wall time roughly 3x. The turn still blocks until all finish, so this composes with option 1 (warm words) or rides INSIDE an option 3 background session, where blocking does not matter and the batch finishes faster.

Found in codeeve/docs/concepts/default-harness.md:38 (agent tool ships enabled); only bash, write_file, web_fetch are disabled (agent/tools/*.ts sentinels). Depth cap 3 by default.
Watch outLandmine 4 (ledger double-writes from child sessions) must be settled first. Also per-child image spend multiplies; the 30/day image cap is family-wide.
ImpactWall time only, and only for batches. Usage data should justify it before instructions encourage it.
6

The full orchestrator

XL · changes the product's shape

The eleven-star version of the screenshot: multiple named background jobs with live progress cards in chat (attach to each background session's own NDJSON stream; the run row already stores the runtime session id via setTaskRunRuntimeSession), a jobs drawer, cancel buttons, and a completion notification policy that follows her across channels (toast if the tab is open, text if she left, quiet hours respected). This turns chat from a conversation into a mission control, which is a product decision before it is an engineering one.

Found in codeSession ids per run: lib/conversation-continuity/delivery-ledger.ts. Stream route exists per session: GET /eve/v1/session/:id/stream.
UnverifiedWhether a browser bearer can stream a dispatch-principal session (eve route auth). Whether concurrent background sessions stay within Vercel and cost budgets. Notification etiquette has no founder ruling.
ImpactStructural. Do not start here; options 3 + 4 deliver most of the felt value.
