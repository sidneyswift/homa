## Verified meaning and implementation

The existing scorer already computes a credited skill age, a signed difference from the child's age, and a capped positive presentation value. The request does not require changing the scorer, its bank or the child's saved answers. A display cap does not establish that the checklist has no harder questions. The benchmark sources are developmental milestones, standards or typical teaching windows, not a national standardized assessment or percentile.

The comparison builder uses the canonical projection and replays the existing scorer over its effective answers. It finds the answers that actually received the winning credit, preserving each answer's date, source and direct, inferred or unknown derivation. The newest answer is not necessarily the credited answer. Tied support is bounded, with an explicit omitted count. Open conflicts do not become credited evidence. Failed or mismatched reads remain unavailable, distinct from no saved evidence.

Positive web readings use “About N months ahead” or the existing capped “At least N months ahead.” Zero, negative, exposure-only, unknown and conflicting readings do not gain a positive number. Exact limit reasons distinguish the display cap from a confirmed checklist ceiling. Named source references are retained; only public HTTPS URLs become links, so internal catalog references cannot become broken public links.

The live Progress subject row and detail panel use this comparison. The full report must use a projection saved at exactly the same instant, with matching child, scores, bank/scorer and scoring age. Its old payload mixed saved report scores with current compatibility answers, so reconstructing an old report from those answers would invent a measurement basis. The new token-scoped query and validator expose a saved comparison only when that basis matches; older reports without it say the dated basis is unavailable. An authorized parent can open current Progress separately.

Available reports now use every effective answer from that same saved projection in the answer drawer. They do not make a later compatibility read that could race a rescore. Legacy compatibility answers are labeled Current checklist answers. A real PostgreSQL interleaving test commits a rescore between loader reads and proves one request retains its original scores and answers while the next request sees the new revision.

The audit also found a live report-writing race, tracked in [#1124](https://github.com/sidneyswift/homa/issues/1124). A late writer could publish an old letter over a newer report. The released correction ties the claim and final write to the exact report timestamp and a unique generation ID. PostgreSQL microseconds are preserved through explicit text timestamp parameters. The source read uses the same saved comparison answers, and changed-answer evidence is bounded to that report's instant. Superseded writers publish neither stale prose nor misleading completion telemetry. This correction shipped in `66131afd`. The 45 disposable PostgreSQL revision/claim/source cases establish deterministic race behavior; the partial hosted comparison observation does not establish a real concurrent publication race.

The canonical subject read also returns a separate bounded saved-answer inventory with dates, direct/inferred/unknown provenance and exact single-answer credited ages. This preserves lower-credit and Not yet answers that do not appear in the winning basis. Its omitted count prevents a partial inventory being described as the complete record.

The fleet progress-reading skill explains the returned reading without recording answers, starting a check-in or choosing practice automatically. Its read-only tool rechecks authenticated child/family scope. Dynamic context carries bounded canonical comparisons and explicit omission/failure notices. The stale always-on instruction to confirm signed “chart reads” and always claim progress access was removed. The report writer no longer treats every capped value as exhausted checklist coverage; its source prompt, generated runtime module and versioned sample fixtures were updated together.
