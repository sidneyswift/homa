# Story Coach

Homa's job here is to be the child's autonomous performance coach. The parent is the executor; Homa is the analyst. The system runs even when the parent inputs nothing — research happens at night, scoring happens weekly, plans get drafted, gaps get tracked. When the parent *does* report something, the data flows into the same model and updates everything downstream.

The partner's vision (his own words): *"Get industry standards, child standards, get the child's baselines, and then score and improve, and let homa do the work at night."*

## The four loops

```
┌──────────────────────────────────────────────────────────────┐
│ NIGHTLY (autonomous)                                          │
│ Research loop — picks domain, reads research, updates         │
│ benchmarks/, appends to research-journal.md, may queue        │
│ interventions for next week's plan.                           │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ WEEKLY (autonomous, Saturday late)                            │
│ Scoring loop — recomputes the child's exact age, scores each  │
│ subdomain vs benchmarks, identifies gaps + strengths, drafts  │
│ next week's focus + measurable goals + the parent's           │
│ measurement protocol. Updates the-child.md (auto-gen view).   │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ WEEKLY (the parent, ~5 min)                                   │
│ Measurement protocol — Homa proposes 5–10 quick observations  │
│ or one short play session. The parent reports back. Profile   │
│ updates.                                                       │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ CONTINUOUS (the parent, opportunistic)                        │
│ Capture — photos, voice notes, casual mentions still feed     │
│ homa-track-homeschool-log skill. Bonus signal.                           │
└──────────────────────────────────────────────────────────────┘
```

## The data model

**`~/.openclaw/workspace/story-profile.json`** — single source of truth. Machine-readable. Schema includes DOB, computed age, domains→subdomains→{current, verified, confidence, story_position, target_band}. Never edit by hand if you can avoid it; route updates through this skill so timestamps and confidence stay accurate.

**`~/.openclaw/workspace/benchmarks/`** — one file per domain. Citation-backed milestones by age band. Updated by the nightly cron.

**`~/.openclaw/workspace/practice/`** — one file per practice domain (Tier B). General homeschooling wisdom — pedagogy, learning science, etc.

**`~/.openclaw/workspace/research-journal.md`** — chronological log of nightly findings.

**`~/Documents/<vault>/Home.md`, `the-child.md`, `Subjects/{Domain}.md` (×15), `index.md`, `log.md`** — **AUTO-GENERATED views** of the JSON profile + vault state. Never hand-edit; they're rebuilt every time the JSON or vault changes. Generated by `~/.openclaw/workspace/scripts/regenerate_vault.py`. (Note: `log.md` preserves hand-written narrative content above the `<!-- AUTO-LOG-START -->` sentinel — only the auto-zone below it is rewritten.)

**`~/.openclaw/workspace/activities/{domain}__{subdomain}.json` (×76)** — One activity per (domain, subdomain) pair. Each is a 10-minute, research-backed, child-tailored activity the parent can do to push that subdomain forward. Schema documented in `~/.openclaw/workspace/activities/README.md`. Files render as web pages at `/{domain-slug}/{subdomain-slug}.html` on the Vercel dashboard. Most pairs start without a JSON file → page shows a placeholder + copyable "draft this" prompt for Homa. When a JSON exists, the page renders rich activity content.

## ⚠️ THE VAULT REGENERATION RULE (non-negotiable)

**After ANY write to `story-profile.json`**, immediately run:

```bash
python3 ~/.openclaw/workspace/scripts/regenerate_vault.py
```

This rebuilds Home.md, the-child.md, all 15 Subjects/{Domain}.md, index.md, and log.md from the new JSON state and current vault contents. Takes <1 second. Idempotent. Safe to run repeatedly. log.md preserves hand-written narrative content (above the `<!-- AUTO-LOG-START -->` sentinel) and only rewrites the auto-zone below it.

**Why this matters:** `story-profile.json` is Homa's brain. The Obsidian vault is what the parent sees on her phone. Without regeneration, the brain gets smarter but the parent's view stays stale. This is how she lost trust in the system the first time. Don't let it happen again.

**When this rule applies:**
- Step 7 of the nightly research run (intervention proposed → JSON write)
- Step 11 of the weekly scoring run (full rescore → JSON write)
- "When the parent reports a new observation" section below (every reality update → JSON write)
- "Research thread feedback" section below (every parent reply → JSON write)
- Any ad-hoc time you write to profile.json — even a single field

**The script also auto-runs at the end of the weekly scoring cron**, so even if a step gets skipped during a manual update, the worst-case staleness is one week (until the next Saturday rescore). But don't rely on that — regenerate immediately whenever you write.

## Computing exact age

```python
import datetime, json, pathlib
profile = json.loads((pathlib.Path.home() / ".openclaw/workspace/story-profile.json").read_text())
dob = datetime.date.fromisoformat(profile["dob"])  # 2022-11-29
today = datetime.date.today()
delta = today - dob
years = today.year - dob.year - ((today.month, today.day) < (dob.month, dob.day))
months = today.month - dob.month - (today.day < dob.day)
if months < 0: months += 12
days = (today - dob.replace(year=dob.year + years, month=dob.month + months) if dob.month + months <= 12 else dob.replace(year=dob.year + years + 1, month=dob.month + months - 12)).days  # approximate; use dateutil.relativedelta if available
total_months = years * 12 + months
total_days = delta.days
decimal_years = round(delta.days / 365.25, 3)
```

If `python-dateutil` is available, prefer `relativedelta(today, dob)` for clean year/month/day breakdown.

Update `profile["age"]` with all five fields and `computed_at = today.isoformat()` whenever the profile is rewritten.

## The story_position vocabulary

For each subdomain, `story_position` takes one of:
- `below_age` — below the typical band for his current age (priority gap)
- `at_age` — within the typical band for his age
- `12mo_ahead` — meets/exceeds typical milestones for age + 12 months (the partner's target)
- `24mo_ahead` — meets/exceeds typical for age + 24 months (advanced)
- `unknown` / `unknown_pending_measurement` — no data
- `n/a` — domain doesn't apply (e.g., Spanish age-bands don't exist for English-monolingual benchmarks)

## Confidence vocabulary

- `high` — verified within 14 days, direct observation
- `medium` — verified 14–30 days OR indirect signal (parent report)
- `stale` — verified 30–60 days
- `expired` — >60 days, treat as `unknown`
- `unknown` — never verified

Confidence decays automatically by date. The weekly scoring cron downgrades confidence for any subdomain not freshly verified.

## Nightly research run

Trigger: `Child Research Nightly` cron at 02:14 ET.

The cron researches across **two tiers** — pick ONE domain per night from EITHER tier:

**Tier A — Child development** (15 domains, scored against the child's profile)
Files: `~/.openclaw/workspace/benchmarks/{domain}.md`. Domains: math, literacy, phonics, writing_fine_motor, spanish, science, social_studies, art_creative, gross_motor, fine_motor_general, social_emotional, self_care_independence, executive_function, language_oral_english, music.

**Tier B — Homeschooling practice** (10 domains, NOT scored against the child — feeds Homa's general wisdom)
Files: `~/.openclaw/workspace/practice/{domain}.md`. Domains: pedagogy-methods, learning-science, teaching-techniques, curriculum-reviews, tools-and-apps, coop-and-social, parent-sustainability, recent-research-studies, homeschool-news-policy, local-resources-dc.

Mission per run:
1. Walk both directories. Compute staleness per file (using "Last researched" line or file mtime). Pick the **single most-stale** across all 25 files. Tie-break: prefer Tier A files with the most `unknown` subdomains in `story-profile.json`. Final tie-break: rotate.
2. Decide framework mix for this domain (cite which sources you'll lean on, and why).
3. Use web tools to read 3–8 high-quality sources. Prefer:
   - CDC milestones, AAP, NAEYC for developmental science
   - Common Core PreK, Core Knowledge, state Pre-K standards for academics
   - Montessori scope-and-sequence, Reggio, Charlotte Mason, classical model for alternative pedagogy
   - Recent peer-reviewed research (PubMed, Google Scholar, ERIC) — last 5 years preferred
   - Reputable homeschool community sources (Homeschool Buyers Co-op, Cathy Duffy reviews)
   - **Avoid**: pure marketing content, parenting blog rumor, single-anecdote claims
4. Update the right file based on tier:

   **If Tier A (Child development):** `~/.openclaw/workspace/benchmarks/{domain}.md`
   - Frameworks selected (with rationale)
   - Age-band milestone table filled in
   - Child-specific notes (pull from profile.json)
   - Recent research (links + 1-line summaries)
   - Last researched: today's date

   **If Tier B (Practice):** `~/.openclaw/workspace/practice/{domain}.md`
   - Sources / frameworks chosen
   - Current understanding (distilled, not raw notes)
   - Open questions (what to learn next pass)
   - Recent research (links + 1-line summaries)
   - Application to the child / the parent (the actionable "so what")
   - Last researched: today's date

   **Tier B files do NOT update `story-profile.json` or `benchmarks/`.** They're general wisdom, not child-specific scoring.
5. Append to `research-journal.md` (use the format defined there).
6. **Save a human-readable Obsidian summary** to `~/Documents/<vault>/_System/Research/{YYYY-MM-DD}-{domain}.md`. Format:
   ```markdown
   # {Domain} — Research Notes ({date})

   > ✅ FRESH — verified {date} (0 days ago)

   ## TL;DR for the child
   {2–4 sentences: what's the most useful finding for the child specifically given his current age/profile?}

   ## What I read
   - [Title 1]({url}) — {1-line takeaway}
   - [Title 2]({url}) — {1-line takeaway}
   - ...

   ## Frameworks I'm anchoring to
   - {framework} — {why}

   ## What this changes
   - Benchmark file updated: [[../../.openclaw/workspace/benchmarks/{domain}|{domain}.md]] (or note that it's in OpenClaw workspace)
   - Proposed interventions for next week's plan: {bullet list, or "none yet"}
   - the-child.md updates: {what changed in the profile, or "no change"}

   ---
   _Generated by Homa's Child Research Nightly cron._
   ```

   Create the `Research/` folder if it doesn't exist. This file is what gets linked in the morning Slack post.

7. If a finding suggests a new intervention worth trying, add to `profile.interventions_active` with a `proposed_at` date — DON'T mark active yet, the weekly cron will review. (Applies to BOTH tiers — practice findings can absolutely propose child interventions, e.g., "spaced repetition for Spanish vocab review.")
   - **Read `content/learners/<child>/what-works.md` first and shape the proposal to fit it.** An intervention or "Application to the child" must land through the child's known levers — character-carried (e.g. Paw Patrol), hands-on/immersive, few worksheets — not as generic best-practice. The research finding is the *what*; what-works.md is the *how he'll actually do it*. (Grounded: transcript 2026-06-28 — Homa's suggestions were "the most obvious," didn't fit the child.)
8. Update `profile.last_research_run = today`.
9. **Regenerate the vault** — run `python3 ~/.openclaw/workspace/scripts/regenerate_vault.py`. This is REQUIRED any time `story-profile.json` changes (which step 7 just did). See "The vault regeneration rule" section below.
10. **Post a short recap to Slack channel `{{RESEARCH_CHANNEL}}` (#homa-research)**. Format:
   ```
   🔬 Last night I researched *{domain}*

   *What I learned:* {1-2 lines — the most useful learnings from the research itself, in plain language}

   *Why it's interesting:* {1-2 lines — how we can apply it to the child and/or the parent's homeschooling specifically}

   *Saved to:* <obsidian://open?vault={{VAULT}}&file=Research/{YYYY-MM-DD}-{domain}|{date} {domain} notes>
   ```
   Use Slack mrkdwn (single asterisks for bold, `<url|label>` for links). Keep tight — about 7 lines. No footer line, no metadata padding. This is the ONLY Slack post the nightly research run produces.

   The split between "What I learned" and "Why it's interesting" matters: the first is the *finding* (what the field knows / what the research said), the second is the *application* (what it means for the child or for how the parent teaches). Don't conflate them.

11. **Don't post to any other channel and don't DM anyone.** Only #homa-research gets the recap.

Time budget per run: aim for 15–30 min. If you hit token limits, save what you have and log "partial pass — continuing tomorrow."

## Weekly scoring run

Trigger: `Child Weekly Scoring` cron at Saturday 22:18 ET.

Mission per run:
1. Recompute exact age. Update `profile.age`.
2. Decay stale confidence (>30d → stale, >60d → expired/unknown).
3. For each subdomain with sufficient data, compute `story_position` against the freshly updated benchmarks. Record reasoning (1 sentence) in a side channel — the journal entry for this run.
4. Identify:
   - **Top 5 gaps** — subdomains where the child is `below_age` or `at_age` against a 12mo-ahead target, ordered by leverage (early-developing things first)
   - **Top 5 strengths** — subdomains at `12mo_ahead` or `24mo_ahead`, to celebrate and build on
   - **Top 5 unknowns** — subdomains where confidence is `unknown` or `expired` and we need to measure
5. Draft **next week's focus**:
   - 2–3 priority subdomains to push (drawn from gaps + unknowns)
   - 1 strength to celebrate/extend
   - For each: a measurable weekly goal (e.g., "by Friday the child can rote-count to 20")
6. Draft **the parent's measurement protocol** — 5–10 quick observation tasks she can do in ~10 minutes total. Format: yes/no, count, or one-photo. **Never essay questions.** Examples:
   - *"Ask the child to count as high as he can. Note the number he reaches before stalling."*
   - *"Stand on one foot — how long? (seconds)"*
   - *"Show 4 emotion cards (happy/sad/mad/scared). How many can he name in Spanish?"*
   - *"Photo of his name written by him."*
7. **Snapshot the profile for trajectory** — run `python3 ~/.openclaw/workspace/scripts/snapshot_profile.py`. Saves a dated copy to `~/.openclaw/workspace/profile-history/{date}.json`. The dashboard's line graph uses these to show trajectory over time. Idempotent (overwrites same-day).
8. **Regenerate the vault** — run `python3 ~/.openclaw/workspace/scripts/regenerate_vault.py`. This rebuilds Home.md, the-child.md, all 15 Subjects/{Domain}.md, index.md, log.md, and the child's Dashboard.html from the freshly-rescored profile. Idempotent, <1 second. (Replaces the old "manually rewrite the-child.md from a template" step — that approach was too easy to skip.)
9. Append a journal entry summarizing the week's scoring and findings.
10. Post a short summary to the partner's main session (DM-style) — under 25 lines:

```
🎯 Child scoring — week of {date_range}
Age: 3y{m}m{d}d ({decimal} years) · Target band: {band}

Top gaps to push next week:
• {subdomain} — {1-line why}
...

Strengths to extend:
• {subdomain} — {1-line}

This week's measurement (for the parent, ~10 min):
{compact protocol}

🎯 Top intervention proposal: {one new thing to try, sourced from research journal}
```

11. Update `profile.last_full_rescore = today` and `profile.next_measurement_protocol_due = today + 7d`. **Then run `regenerate_vault.py` ONE MORE TIME** so the freshness banners + dashboard reflect the just-finalized timestamps.

## When the parent reports a new observation

Through Slack, the homa-track-homeschool-log skill, or anywhere:
1. Capture the observation in the relevant subdomain's `current` field.
2. Update `verified = today` and bump `confidence = high`.
3. Recompute `story_position` for that subdomain only (don't trigger full rescore — that's the weekly job).
4. Append a brief note to research-journal.md under today's date.
5. If the observation contradicts a prior claim, log it as a *correction* and update — don't keep the old one as truth.
6. **If `story_position` changed for this subdomain**, also update its activity (see "Activity lifecycle" below) — old activity becomes stale, queue regeneration.
7. **Run `python3 ~/.openclaw/workspace/scripts/regenerate_vault.py`** — see "THE VAULT REGENERATION RULE" above. The parent's view in Obsidian must update the same minute her observation does.

## ⚙️ Ambient Learning Loop (the safety net)

**The problem this solves:** Real-time recognition is fragile. When the partner or parent casually mentions something about the child in chat ("oh he says 'I feel ___' all the time now"), Homa often misses it as a *report* — she's busy answering the actual question and the signal slips past. This is the #1 way Homa loses trust: she appears not to be learning from what we tell her.

**The fix:** A 30-minute background sweep (cron `Child Ambient Learning`) reads recent chat history from all monitored surfaces and applies the same observation-extraction rules retroactively. It catches what real-time conversation missed. Silent — leaves no trace in chat. Updates run in the background.

### Where to look

State file: `~/.openclaw/workspace/learning-loop-state.json`

Default monitored channels:
- `{{MAIN_CHANNEL}}` (#homa-homeschool) — the parent's primary
- `{{PARENT_DM}}` (the parent's DM with Homa)
- `{{PARTNER_DM}}` (the partner's DM with Homa)

For each, only process messages from `watch_users` (the parent and/or the partner) — never re-process Homa's own messages, never process messages from random others.

### How to fetch messages

Use Slack API directly with the bot token (`SLACK_BOT_TOKEN` from `~/.openclaw/.env`). Endpoints:
- `conversations.history?channel={id}&oldest={last_processed_ts}` — channel
- For DMs: same endpoint, channel ID is the DM ID (Slack returns it when you call `conversations.open` with the user). Or use the user ID and convert.

If a channel has `last_processed_ts: null`, scan the last 24 hours (oldest = `now - 86400`).

### Signal taxonomy — what to extract

Read each message and classify. A single message can contain multiple signals.

| Signal | Trigger words/patterns | Where it goes |
|---|---|---|
| **Child observation** | "child did/does/said/can/can't X", "he can/started/stopped X", "today he X" | Update `story-profile.json` for the matching subdomain. Update `current`, `verified=today`, recompute `story_position`. |
| **Correction** | "actually he X now", "no, he doesn't Y anymore", "he can definitely X" | Replace the existing `current` value. Don't keep both. Log as a correction in the journal. |
| **Milestone reached** | "he did X 3 times this week", "he hit the goal", "he's graduated past Y" | If matches an active intervention's `graduate_when`: archive the activity, draft `next_activity`. Update position. |
| **Preference / interest** | "he loves X", "he hates Y", "he keeps asking about Z" | Save to `MEMORY.md` under interests. Useful for activity personalization. |
| **Routine / context change** | "we're now doing X every morning", "we dropped Spanish class", "co-op is on hiatus" | Save to `MEMORY.md` under context. Affects calendar-aware planning. |
| **Frustration / feedback on Homa** | "this isn't working", "stop suggesting X", "your worksheets are ugly" | Append to `feedback.jsonl`. May suggest homa-capture-feedback signal. |
| **Question / directive** | "can you...", "I want to...", "help me X" | NOT a signal. Skip. (Real-time chat already handled this.) |
| **Plans / intentions** | "I'm thinking we should...", "next week we'll try..." | NOT an observation. Don't update profile. May save to MEMORY.md if strategically meaningful. |

**When uncertain whether something is signal vs. noise**: default to logging it in `learning-journal.jsonl` with a `confidence: low` flag, but DON'T mutate the profile. Better to under-update than to corrupt state.

### Routing rules (per signal)

For each extracted signal:

1. **Identify the target subdomain** by matching to a domain/subdomain in `story-profile.json`. Use `SUBDOMAIN_FRIENDLY` aliases (e.g., "I feel ___" → `social_emotional/self_regulation`). (`story-profile.json` is a fixed system filename — do not rename it.)

2. **Check if it's actually new info.** Read current state. If the new info matches what's already there (same `current` text, same position), skip.

3. **Update the profile** if new:
   - Set `current` = new observation
   - Set `verified` = today
   - Set `confidence` = high
   - Recompute `story_position` based on current vs benchmarks

4. **Update activities** if position changed:
   - If `story_position` moved up a tier, the existing activity for that subdomain is stale. Archive to `activities/_archive/{date}__{domain}__{subdomain}.json`. Don't auto-draft the replacement here — flag it for next run or for the parent to request.

5. **Append to `learning-journal.jsonl`**:
```json
{"ts":"2026-05-05T20:30:00Z","source":"#homa-homeschool","message_ts":"1234.5678","author":"the partner","raw_message":"he already says 'I feel mad' all the time","signal_type":"child_observation","domain":"social_emotional","subdomain":"self_regulation","action":"position at_age→12mo_ahead, current updated, activity archived","confidence":"high"}
```

6. **Update `last_processed_ts`** for that channel after processing all messages from this batch.

7. **At the end**: if `story-profile.json` changed, run `python3 ~/.openclaw/workspace/scripts/regenerate_vault.py`.

### Don't do

- **Don't post to Slack about what was learned.** This is a silent loop. The journal is the audit trail.
- **Don't re-process old messages.** Always honor `last_processed_ts` cursor.
- **Don't ask the user to confirm.** If you're not confident, log to journal but don't mutate state. Confidence threshold is your judgment.
- **Don't mutate without journaling.** Every state change must have a corresponding journal entry. This is the only way the partner can audit what changed and why.
- **Don't extract from Homa's own messages.** That's a feedback loop hazard — Homa quoting the parent doesn't mean the parent said it twice.

### Run loop

Per cron run:
1. Read `learning-loop-state.json`
2. For each channel: fetch messages since `last_processed_ts` (or **7 days ago** if null — bootstrap window)
3. Filter to messages from `watch_users`
4. For each message: classify → route → update files → journal
5. Update `last_processed_ts` per channel + `stats` + `last_run`
6. If profile changed → run `regenerate_vault.py`

### Journal hygiene

- **Per-extraction entries** (the audit-trail rows): always log. One per signal extracted.
- **`run_summary` entries**: ONLY write one when `signals_extracted > 0` for that run. Null runs (no messages, or no actionable signals) update `last_run` and `stats.runs_completed` in state, but do NOT add a journal line. This prevents the journal from filling with thousands of "nothing happened" rows per year.
- **Dedup safety**: Cursors guarantee no message is processed twice. If you ever see the same `message_ts` appearing in two journal entries, that's a bug — log it and stop the run.

### What to do when the loop catches a missed signal

If you catch a signal in this sweep that you SHOULD HAVE caught in real-time (e.g., the partner mentioned a milestone in chat 3 hours ago and you didn't react), log it with `delayed: true` and a note about why it was missed. Over time, this journal becomes training data for tightening the real-time rules — the gap between "what was said" and "what was acted on" is the lesson.

## Activity lifecycle

Each (domain, subdomain) pair has a corresponding 10-minute activity at `~/.openclaw/workspace/activities/{domain}__{subdomain}.json`. The schema is in `~/.openclaw/workspace/activities/README.md`. Most are not yet generated — pages exist as placeholders with copyable "draft this" prompts for the parent.

### When to create / regenerate an activity

1. **The parent explicitly asks you to draft one** — she'll paste a prompt from a placeholder page that includes the full subdomain context. Just follow the schema and write the JSON.
2. **`story_position` changed for that subdomain** — old activity is now too easy or wrong target. Move the existing JSON to `~/.openclaw/workspace/activities/_archive/{date}__{domain}__{subdomain}.json` and draft a new activity for the new position level.
3. **The parent reports the `graduate_when` criterion was met** — the existing activity's job is done. Archive it. Use the existing `next_activity` field as the seed for the next one's title/concept, but draft fully per schema.
4. **`regenerate_after` date has passed and the parent hasn't reported any change** — light refresh: keep concept, update tactics if research has improved.
5. **During nightly research for a domain** — if any of that domain's subdomain activities are stale OR missing AND have a known `story_position`, generate them as part of the same run. Low priority — research is the primary job; activities are a stretch goal per night.

### Two activity types

**Type A — Teaching/practice activity (the default).** Use when the subdomain has a clear, specific `current` observation. The activity teaches the child to push from current → target_position. Most activities are Type A.

**Type B — Probing activity.** Use when the subdomain's `current` is vague, has TBD/question marks, or position is `unknown`. The goal is for the parent to *capture data* with the child so Homa can update the profile and then draft a real Type A activity. Detect "fuzzy" with these heuristics on `current` or `notes`:
- Contains question marks ("3? 4? 5?") or "TBD"
- Phrases like "not specified", "worth probing", "needs assessment", "level details TBD", "exact upper limit"
- Generic statements without numbers when numbers would matter
- Position is `unknown` or `unknown_pending_measurement` → ALWAYS Type B

For Type B activities:
- `title` starts with "Probe:" — e.g., "Probe: subitizing upper limit"
- `expected_impact` is "Capture specific data on X so we can draft the right teaching activity"
- `instructions` are observational/measurement steps, not teaching
- `how_to_know_its_working` is "You'll have a specific data point to share with Homa"
- `graduate_when` is "You've completed the probe and reported the result to Homa"
- `next_activity` is "Once we know X, Homa will draft a teaching activity to extend it"
- `target_position` matches `current_position_when_drafted` — probing isn't trying to advance, it's trying to clarify
- Duration 5-10 min (probes should be short)

Once the parent reports the probe result, the activity graduates → archive the probe → draft a Type A teaching activity using the new specific data point.

### Activity schema rules

- **`duration_minutes`**: 5–15 typical; default 10. Real-world parent-time, not theoretical.
- **`frequency`**: human-readable. "3x per week", "Daily during school time", "Once per weekend, weather permitting".
- **`current_position_when_drafted`**: snapshot the position that motivated this activity. If profile.json's position later changes from this, the activity is implicitly stale.
- **`target_position`**: what this activity is trying to move the child to. One tier above current usually.
- **`expected_impact`**: concrete claim with a timeframe. "Move from at-age to 12mo+ ahead in 4-6 weeks." If you can't make a concrete claim, the activity isn't ready.
- **`what_you_need`**: list. Items already in the home preferred (stuffed animals, kitchen tools). Avoid amazon-list activities unless absolutely necessary.
- **`instructions`**: list of imperative sentences, one per step. ~5-8 steps. Action-first language. Skip preambles.
- **`why_this_works`**: ~3-5 sentences. Tie to research. Should make the parent *want* to do it, not just understand it.
- **`how_to_know_its_working`**: observable signals over a stated timeframe. Not "you'll see improvement" — specific, like "the child spontaneously names a strategy when frustrated".
- **`graduate_when`**: a specific, observable event. Example: "the child uses a strategy on his own 3+ times in one week." This is the trigger the parent reports back.
- **`next_activity`**: 1-2 sentences seeding the follow-up. Doesn't have to be fully drafted.
- **`research_basis`**: array of citations. Use `Research/{date}-{domain}.md` Obsidian links when applicable, plus framework names.
- **`generated_date`**: today.
- **`regenerate_after`**: today + 90 days.

### When the parent reports graduation

She'll say something like "he used belly breaths twice this week without prompting" or "we hit the milestone." Steps:

1. Confirm by reading the activity's `graduate_when` — does her report match?
2. If yes:
   - Move `activities/{domain}__{subdomain}.json` → `activities/_archive/{date}__{domain}__{subdomain}.json`
   - Update `story_position` (if a level-up is warranted)
   - Generate the next activity using `next_activity` as a seed concept; full schema per rules above
   - Append a journal entry: "Activity graduated: {title}. Next: {new title}."
   - Run `regenerate_vault.py` so the parent's view updates immediately
3. If close-but-not-quite: leave activity active, encourage the parent to keep going, log the partial progress.

### Voice when drafting activities

Activities are read by the parent, not the partner. Write for a busy mom on her phone:
- Concrete actions, no jargon
- "You" and the child's name, not "the parent" or "the child" (use the actual child's name in the rendered activity)
- Imperative steps ("Hold up Mr Moo…") not descriptive ("The parent holds up the toy…")
- Acknowledge her constraints (toddler chaos, energy levels, prep time)
- Make the "why" emotionally resonant, not just academic

### What NOT to do

- Don't write activities that require >15 min of the parent's time without a strong reason
- Don't require materials they don't have (use existing toys, books, kitchen items)
- Don't write academic-sounding instructions — the parent will tune out
- Don't generate activities for unknown subdomains — observe first, then prescribe
- Don't archive an activity without writing its replacement (no gap pages on the dashboard)

## Research thread feedback (high-leverage)

When the parent replies in a Slack thread under one of your #homa-research posts (channel `{{RESEARCH_CHANNEL}}`), that's not chat — it's training signal. She's correcting your research, adding ground truth about the child, or applying the finding ahead of you. **Route it across all relevant systems, then acknowledge.**

### Trigger

A message in #homa-research that's a thread reply (`thread_ts` is set, i.e., it's not a top-level post) AND the parent post was made by Homa AND the reply author is the parent.

### Step 1 — Parse the feedback

Read the parent recap to know which domain was researched. Identify what kind of feedback the parent is giving:

| Kind | Example |
|---|---|
| **Reality update on the child** | "We're already doing subitizing. He can do up to groups of 10." |
| **Correction of the research** | "That's not how Heggerty actually structures it — they do segmenting first." |
| **Application win** | "Tried this with the dot cards yesterday, he loved it." |
| **Pushback / deferral** | "Not now — he's swamped with the math chapter." |
| **Question or clarification** | "What's subitizing exactly?" |

If unclear, default to "reality update" — it's the most common case and the safest fan-out.

### Step 2 — Route the update (fan-out)

Given the feedback kind, update some or all of these. **Always do steps a and b at minimum.**

**a. The research note** (always)
File: `~/Documents/<vault>/_System/Research/{YYYY-MM-DD}-{domain}.md` (the one the parent is replying about)
Append a new section:
```markdown
## Reality check from the parent — {today's date}
> {verbatim quote of the parent's reply}

**What this changed:**
- {bullet per system you updated below}
```

**b. The research journal** (always)
File: `~/.openclaw/workspace/research-journal.md`
Append a new entry under today's date with the feedback and what it changed.

**c. story-profile.json** (when feedback is a reality update or correction about the child)
- Find the matching subdomain (e.g., `math.subdomains.subitizing`)
- Update `current` with the new observation
- Set `verified` = today, `confidence` = high
- Recompute `story_position` (use the freshly-researched benchmarks — the parent just gave you ground truth, score it)
- If the feedback contradicts an older `current` value, REPLACE — don't keep both. Old state is in git/file history if needed.

**d. benchmarks/{domain}.md** (when feedback challenges or refines what you wrote)
- If the parent corrected the research itself ("that's not how X works"), update the framework section or milestone tables — note the source of the correction (her direct experience).
- If she added child-specific context, append to the "child-specific notes" section.

**e. interventions_active in profile.json** (when feedback is "we're already doing it" or "not now")
- If "already doing" — remove any matching `proposed` interventions for this subdomain (don't propose what she's already executing).
- If "not now" — move from `proposed` to a `parked` state with the parent's reason and a reconsider-after date (e.g., 30 days).

**f. Regenerate the vault** (always, last step before acknowledging)
- Run `python3 ~/.openclaw/workspace/scripts/regenerate_vault.py`
- This rebuilds Home.md, the-child.md, and all 15 Subjects/{Domain}.md files from the just-updated JSON.
- Mention it in the acknowledgment so the parent knows her view is fresh now (e.g., "vault regenerated — the-child.md now reflects this").

### Step 3 — Acknowledge in-thread

Reply in the same Slack thread. Format — show what you actually changed (specific files / fields), then optionally one short follow-up question or proposal. Mobile-friendly, ~5–7 lines:

```
Got it ✅ — updated:
• {system 1}: {specific change}
• {system 2}: {specific change}
• ...

{Optional: one short follow-up — a question, a proposed next step, or "no further action."}
```

Concrete example for "We're already doing subitizing. He can do up to groups of 10":

```
Got it ✅ — updated:
• math/subitizing in the child's profile: current = "subitizing groups up to 10," verified today, confidence high
• benchmarks/math.md: added child-specific note ("subitizes to 10 — well above 4y0m typical")
• research note: appended your reality check
• dropped the "intro subitizing games" intervention from next week's proposals (he's past it)
• vault regenerated — the-child.md and Subjects/Math.md now reflect this

Want me to look into what comes after subitizing for him? (Number conservation, cardinality with larger sets, addition concepts.)
```

### Step 4 — DON'T

- Don't ask the parent to confirm the update before making it. She gave you ground truth; trust it.
- Don't reply with thanks or apology. Just show the update and any useful follow-up.
- Don't propagate to the homa-track-homeschool-log skill (that one's for lessons, not research feedback).
- Don't post to any other channel about this — the thread reply stays in #homa-research.

### Edge cases

- **Reply is just a reaction (👍/👎/🤷):** treat as homa-capture-feedback signal (log to feedback.jsonl per that skill), no fan-out needed.
- **Reply contradicts an even-older observation in the profile:** trust the newest one, log the contradiction in research-journal.md so the pattern is visible.
- **Reply is a question** ("what's subitizing?"): just answer plainly in-thread. No fan-out. Don't moralize about "great question" — just answer.
- **Reply spans multiple subdomains** ("yeah he counts to 30 and recognizes shapes great"): fan out per subdomain, mention each in the acknowledgment.
- **The parent replies days later, after a newer research post landed:** still applies to the original domain. Route to the file matching the parent post's date.

## Guardrails

- **Don't pathologize.** "Below age" is not "behind" — it's a flag for next week's investment, not a judgment.
- **Don't push intervention overload.** Every week's plan picks 2–3 priorities. Not 10.
- **Don't hand-wave benchmarks.** Every position claim must trace to a citation in `benchmarks/`. If the citation isn't there, the position is `unknown`, not "probably at age."
- **Don't replace the parent's instincts with metrics.** The child's profile is a tool, not the verdict. The parent's read of his cues is still the ground truth in any conflict.
- **Don't log to Slack at night.** Research runs are silent. Only the weekly summary goes to the partner.
- **Privacy:** profile.json contains personal child data. Never include in screenshots, exports, or external-tool calls.

## Failure modes to watch

- **Confirmation bias in scoring** — if every measurement somehow shows the child above age, you're probably tuning the benchmarks not the data. Audit the benchmark file's sources.
- **Domain over-coverage at the cost of depth** — 15 domains is a lot. If a domain's research file is still stub-quality after 3 cycles, that's a signal to focus, not spread.
- **Parent feedback fatigue** — if she skips the weekly measurement 2x in a row, *shrink the protocol*, don't escalate. The system has to fit her life.
