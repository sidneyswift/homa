## 1. Goal / Spec

### Objective
Raise the share of Homa-generated learning materials (worksheets, printables, packets) that a parent approves **on first delivery**, instead of going through several rounds of correction. The founder's own words: "she is generating things that require the user to correct her ALOT... we need to think about a way for Homa to get closer to generating materials that are usable on first delivery."

This was scoped in two phases:
1. **Research phase** (complete): read a month of real production chats, extract delta buckets (what parents actually corrected, and why), rank solutions easiest-to-hardest × most-likely-to-help, write it up as a trackable plan.
2. **Implementation phase** (in progress): actually build the highest-leverage fixes identified by the plan, starting with the deterministic geometry/measurement work that the plan and a parallel field-study arc both independently converged on as the single highest-impact item.

### Definition of done
- The plan doc exists, is verified against production data, and is merge-reviewed against overlapping work so nothing is built twice.: **done**, see §2.
- The `cutoff-page-is-a-block` founder ruling (2026-07-29) has real code behind it: a page a deterministic measurement PROVES is physically cut off is never delivered; Homa rebuilds and says she caught a problem, not that a tool failed.
- The materials QC brief carries the child's age (previously absent, which made two of the reviewer's own stated criteria unsatisfiable).
- Fixed-dimension formats (flash cards) are exempt from the "scale to fill" underfill law, since filling them defeats their own physical-card-size purpose.
- The rest of the waved plan (`docs/homa-planning/plans/2026-07-28-materials-first-delivery-approval.md`) executes in priority order, tracked via gh#362 and the reuse map in that doc's §7.

### Known gotchas / landmines
- **CI eval red on your branch, green on `main`, same day = investigate, don't dismiss.** This repo's memory/culture is "CI eval red means nothing" (main itself fails 4-5 evals per run, the failing set churns): that's true for chronic flakes like `materials-studio/lesson-plan-routing`. But when a specific eval passes cleanly on `main`'s own baseline run and fails on your branch in the same time window, that pattern is real signal. This happened in this session: `materials-studio/packet-page-revision` passed 7/7 on main, failed 3/7 on this branch, with a "two near-identical `create_printable` calls, neither `created: true`" signature.
- **Root-caused via a standalone render probe, not the eval harness.** The eval harness needs a `VERCEL_OIDC_TOKEN` (`pnpm dev:token`) which failed in this worktree (no `.vercel` project link: each git worktree needs its own, and `apps/web/.vercel` is gitignored). Rather than blocking on that, I wrote a throwaway script that imports `wrapPrintableDocument` + `renderPrintableHtml` directly and renders the eval fixture's actual seeded HTML through the real pipeline with zero model/DB dependency: this needs only a local Chrome, no auth. **This is the technique to reach for whenever a materials-rendering question needs a definitive answer and the model/eval layer is unavailable or too slow to iterate against.** The script was deleted before commit (`apps/web/probe-fixture-geometry.mts`, not shipped): recreate it if you need to re-verify anything similar; it's ~90 lines, described in the commit message of `998825bb`.
- **The actual bugs found, for anyone re-deriving this:**
  1. `provenCutoffPages` was checking every rendered page of a packet, including pages carried over unchanged via `fromMaterialId`. A parent revising ONE page of an already-`final` 12-page packet could get the whole revision refused because some OTHER, untouched, previously-approved page happened to measure past the edge: which is backwards from what the founder ruling intended (catch a problem in what Homa is BUILDING, not re-litigate something already shipped). Fixed by scoping to `resolvedPages[i].fresh`, mirroring the exact same distinction `selectPagesForReview` already draws for the review-coverage feature.
  2. The eval fixture's illustrated page (`EVAL_FIXTURE_PACKET_ILLUSTRATED_PAGE = 3` in `apps/web/lib/family-context-eval-fixture.ts`) has genuinely overflowed the physical page since it was authored: proven by directly rendering the seeded HTML. Six block-level `<figure>` elements with no layout CSS stack VERTICALLY (~5.6in) instead of flowing as the "animal-row" its own class name promises, because the fixture has no stylesheet and nothing ever gave `.animal-row` a `display: flex`. This was invisible until `cutoff-page-is-a-block` finally enforced what geometry had only been noting as advisory text before. Fixed with an inline `style="display:flex;flex-wrap:wrap;gap:8px;"`, matching the fixture's own existing convention of inline styles.
  - **Residual uncertainty, not fully resolved by this session:** even after fixing both bugs above, the fixture's filler text alone occupies ~80% of the printable area on every page (`"blend and read. ".repeat(216)` per page, deliberately sized to real-packet-scale for a DIFFERENT eval's cost-gate test: see the comment at `evalFixturePacketPageBodies()`). This leaves only ~1.86-3.36in of headroom on the illustrated page for a "make the animals bigger" edit before it genuinely overflows again. Whether the real model, given my new geometry note's guidance, converges within that headroom on a real CI run is a judgment-dependent question I could not fully verify locally (no OIDC access in this worktree): my synthetic test used a deliberately aggressive 2.5x size increase and DID overflow, which may or may not reflect what a real reasoning model would do. **Check the actual CI eval result for `materials-studio/packet-page-revision` on the latest push (`998825bb`) before assuming this is fully resolved.** If it still fails, the fixture's filler text density (not just the illustrated page's art) may need reducing, or the skill may need explicit guidance that enlarging art on a dense page permits trimming other content on the same page to make room.
